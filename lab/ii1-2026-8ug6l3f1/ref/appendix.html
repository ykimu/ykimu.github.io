    A.1わからないことの調べ方

    コマンドの使い方は、まず手元で調べられる。man コマンド名 は公式マニュアル（英語だが最も正確）、コマンド名 --help は簡易ヘルプである。エラーメッセージで検索するときは、自分の環境固有の部分（ファイル名など）を除いた核心部分で検索するとヒットしやすい。生成AI（第6回 6-6に利用ルールがある）に聞くのも有効だが、「なぜそのコマンドで解決するのか」を説明できるまで理解してから実行すること。理解せずに実行したsudoコマンドは、サーバ管理では事故のもとである。

    A.3資格という道しるべ

    本実習で扱った内容は、Linux技術者認定試験（LinuC レベル1 / LPIC-1）の出題範囲と大きく重なっている。資格の取得自体が目的である必要はないが、出題範囲は「Linux管理者に求められる知識の地図」として優れているため、学習の次の一歩を決める道しるべに使える。クラウド（AWS等）の入門資格も、本実習のインフラ知識の自然な発展先である。

    A.4自宅で続けるには

    本実習の環境は、自宅でも安価に再現できる。Raspberry Pi一式（あるいは古いノートPC＋Linux）でサーバを立て、家庭内LANで友人と遊ぶところまでは本資料の知識だけで到達できる。さらに進んで学外（インターネット）に公開する場合は、固定回線のポート開放・DDNS・攻撃対策（fail2ban、公開鍵認証、更新の自動化）といった新しい課題が現れる。それらは本実習で学んだ原則、すなわち最小権限、デフォルト拒否、バックアップ、ログ監視の延長線上にある。手を動かし続けることが、最良の学習である。

    学習ロードマップ

    次に何を学ぶかは、A.3で触れた資格の出題範囲を地図として使うと決めやすい。本実習の各章がどのあたりに対応するかを示す。

    実習で扱った内容LinuC レベル1 / LPIC-1 のおおよその対応領域次の一歩
    第1章・第2章・第3章・第4章コマンドライン操作、ファイルとディレクトリの管理、テキスト処理正規表現とパイプの練習、アーカイブと圧縮

    本の選び方にも目安がある。第一に、対象バージョンが新しいこと（systemdとDebian 12を前提にしているか）。第二に、写経して動かせる手順が載っていること。第三に、範囲を欲張っていないこと。1冊目は「Linuxコマンドの入門書」、2冊目は「サーバ構築の実践書」、3冊目に「ネットワークかセキュリティの基礎書」という順が無理がない。無償のものでよければA.2のDebian管理者ハンドブックが3冊分を兼ねる。

    自宅で続けるための最小構成

    自宅で同じことを続けるなら、次の構成でよい。総額は新品でもおよそ1万5千円前後で、古いノートPCにLinuxを入れて代用すれば0円でも始められる。

    • Raspberry Pi 4以降の本体と電源、microSDカード（32GB以上、できればUSB接続のSSD）。書き込みが多いのでSDカードは消耗品と考える。
    • 有線LANケーブル。無線でも動くが、切断の原因を切り分けやすいので最初は有線が楽である。
    • Raspberry Pi OS Lite（64-bit）。Imagerの設定でSSHの有効化と公開鍵の登録まで済ませておくと、モニタとキーボードが要らない。
    • 別のマシン1台（普段使いのPCで足りる）。バックアップの転送先にすると3-2-1ルールの「別の場所」を満たせる。

    この構成のまま第1回から第5回を通しでやり直すのが、最も確実な復習である。家庭内LANに閉じている限り、本実習と同じ注意点がそのまま当てはまる。

    A.5最終課題のテーマ例：まず動かす、それから広げる

    指導書6-1のテーマ表は「向き」を示すだけである。ここでは各テーマについて、最初の30分で動く最小形（まず動かす）と、余裕があれば進む先（広げる）の例を挙げる。どこまで広げたかは評価に影響しない。評価されるのは、動いたものを第三者が再現できるように書けているか、なぜその構成にしたかを説明できているかである（指導書6-5）。したがって、まず最小形を完成させ、記事の骨格を書いてから広げるのが定石である。ここに挙げる例は候補にすぎず、同じテーマの中で別のものを作ってもよい。

    Mod・ゲーム運用

    まず動かす：ContentDBからModを1つ選び、data/mods に展開して world.mt で有効化し、ゲーム内で動作を確認する（補足資料11.7）。依存関係（Dependencies）の確認と、導入前のバックアップまでを手順に含める。

    広げる：複数のModや別のゲーム（gameid の切り替え）を組み合わせて、自分のサーバの「遊び方」を設計する。Modも資産の一部として、バックアップと総合演習の再構築手順に組み込む。Modの更新（新バージョンへの差し替えと戻し方）まで手順化できると運用の記事になる。

    Mod自作（Lua）

    まず動かす：worldmods に数十行のModを置き、チャットコマンドを1つ追加する（例：/hello で挨拶を返す、/where で座標を表示する）。公式ドキュメント（docs.luanti.org）のModding Bookの最初の章で足りる。

    広げる：アイテムやノード（ブロック）を追加し、色や効果を luanti.conf の設定値で変えられるようにする。mod.conf を整え、他の人のサーバにそのまま置けば動く形（配布できる形）にまとめる。

    監視の高度化

    まず動かす：cron で load average・メモリ・ディスク・温度を毎分テキストに追記し、第5回 5-4の Web 監視ページからそのファイルを見られるようにする。第3回 3-5で記録した平常時の値と並べて表示する。

    広げる：しきい値を超えたら通知する（チャットサービスのWebhookやメール）か、記録をグラフにする（Prometheus＋node_exporter＋Grafana のコンテナ構成も Pi 400 で動く）。誤検知をどう抑えるかを書けると監視設計の記事になる。

    セキュリティ強化

    まず動かす：SSHのパスワード認証を無効化（PasswordAuthentication no）し、締め出されたときの復旧手順（モニタ接続でのローカルログイン）を先に検証してから適用する。ufw のルールを見直し、開けているポートの理由を一覧にする。

    広げる：fail2ban を導入し、意図的に失敗ログインを繰り返して検知・遮断されることをログで確認する。SSHのポート変更や許可元IPの限定、Luanti側の権限設計（default_privs）まで含めて「多層防御」として整理する。

    マルチサーバ構成

    まず動かす：compose.yaml にもう1つ game サービス（別ワールド・別ポート、例：サバイバルとクリエイティブ）を追加し、両方に接続できることを確認する。ポートの割り当て表を作る。

    広げる：Web 監視ページを共通の入口にして各サーバの状態を一覧できるようにし、バックアップと監視を全サーバに広げる。ワールドごとの設定（luanti.conf を分ける）とリソース配分（docker stats で比較）を設計として説明する。

    バックアップの高度化

    まず動かす：backup.sh の生成物を scp または rsync で別のマシン（BYOD、または隣の学生のPi）へ自動転送し、転送先からリストアしてワールドが戻ることを確認する（3-2-1ルールの「1つは別の場所に」）。

    広げる：sqlite3 の .backup を使ってサービスを止めずに整合性のあるバックアップを取る。さらに「復元して起動できるか」を自動で検証するスクリプトを cron に載せ、結果を backup.log と Web 監視ページに出す。

    構成管理・自動化

    まず動かす：Ansible を BYOD に入れ（Pythonが必要。WindowsではWSLの中に入れる。またはPi自身を制御側にして localhost に適用してもよい）、第2回から第3回で手作業した内容、すなわち ufw のルール、ユニットファイルの配置、luanti ユーザの作成を Playbook にして自分のPiに適用し、同じ状態になることを確認する。

    広げる：初期状態のPi（隣の学生と協力するか、SDを書き直す）に Playbook を適用して、手順書なしで環境が再現されることを実証する。2回目の実行で変更が0になる（冪等性）ことを示せると、Infrastructure as Code の記事として完成する。

    資産のバージョン管理

    まず動かす：compose.yaml・html・backup.sh・ユニットファイルを Git リポジトリにして履歴を残し、過去の時点の構成をチェックアウトして復元できることを確認する。秘密情報（パスワード等）を含めない工夫を書く。

    広げる：Gitea などをコンテナで自前ホストして push 先にし、push を契機に docker compose up -d が走る仕組み（hook や簡単なスクリプト）を作る。「設定を変えたら履歴に残り、自動で反映される」流れを一気通貫で示す。

    上の8つ以外にも、この実習の延長線上にあるテーマはある。たとえば、イメージのタグ固定と「更新前バックアップ→更新→検証→戻す」までを手順化する更新とロールバック、電源断を意図的に起こして復旧を観察し log2ram や USB SSD 起動で改善する SDカードの信頼性、Pi をアクセスポイント（hostapd＋dnsmasq）にして学内Wi-Fiに依存しない独立LANを作るネットワーク構築、journalctl の入退室ログを日次集計してランキングや異常検知を出すログ解析の自動化、nginx の HTTPS 化（自己署名証明書）とアクセス制御などである。独自テーマとして取り組む場合は、第5回までに教員に相談し、「最初の30分で動く最小形」が何かを一緒に決めておくこと。

    避けた方がよいテーマも書いておく。DDNS やルータのポート開放を伴うインターネット公開は指導書2.4 ネットワーク利用上の注意の規則に反する。Kubernetes（k3s 等）は Pi 400 でも動くが、180分では「入れただけ」で終わりやすい。Java で動く別のゲームサーバへの乗り換えは、この実習の資産がほとんど使えない。テーマ選びの基準は「第5回までに作ったものを部品として使えるか」である。
