    第1章 OSとLinux

    メモリmain memory / RAM
    実行中のプログラムとデータを置く作業机。高速だが揮発性で、電源を切ると内容は消える。free -h で使用量を確認できる。第1章 OSとLinux で詳しく
    ストレージmicroSD / SSD
    プログラムやファイルを保存しておく本棚。低速だが不揮発性で、電源を切っても内容は残る。df -h で空き容量を確認できる。第1章 OSとLinux で詳しく
    サーバserver
    ネットワーク越しにサービスを提供する側の役割の名前。機械の種類ではない。1台のRaspberry PiがSSHサーバとLuantiサーバを同時に兼ねることもできる。第1章 OSとLinux で詳しく
    カーネルkernel
    OSの中核。メモリ管理、プロセス管理、ファイルシステム、ネットワーク、デバイスドライバを担う。「Linux」とは本来このカーネルの名前である。第1章 OSとLinux で詳しく
    ユーザランドuser land
    カーネルの外側で動く領域。シェル、ls などのコマンド、Luantiサーバ本体はすべてここにいる。第1章 OSとLinux で詳しく
    ディストリビューションdistribution
    カーネルにシェル・基本コマンド・ライブラリ・パッケージ管理システムなどを組み合わせた、すぐ使えるOSの完成品。Raspberry Pi OSもその1つである。第1章 OSとLinux で詳しく
    bookwormDebianの版のコードネーム
    Debianの版に付けられた愛称（12はbookworm、13はtrixie）。自分の版は cat /etc/os-release で確かめる。Raspberry Pi OSはDebianを土台にしているため、ネットで手順を探すときは「Raspberry Pi OS」ではなく「Debian」と自分の版の番号やコードネームで調べたほうが情報が見つかりやすい。第1章 OSとLinux で詳しく
    リポジトリrepository
    パッケージが置かれている配布元のサーバ。どこを見に行くかは /etc/apt/sources.list と /etc/apt/sources.list.d/ 以下のファイルに書かれている。第1章 OSとLinux で詳しく
    依存関係dependency
    あるパッケージが動くために必要な別のパッケージ。apt は依存を自動で解決して一緒に導入し、不要になったものは apt autoremove で外せる。第1章 OSとLinux で詳しく
    マニュアルページman page
    コマンドや設定ファイルの公式な説明書。man ls のように引き、/ で検索、q で終了する。節番号（1はコマンド、5はファイル書式）で同名の別内容が区別される。第1章 OSとLinux で詳しく

    第2章 ファイルシステムとディレクトリ構造

    テキストファイルtext file
    バイト列を文字コード（現在はUTF-8が標準）の規則で文字として解釈できるファイル。catで読め、viで編集でき、grepで検索できる。Linuxの設定ファイルはほぼすべてこれである。第2章 ファイルシステムとディレクトリ構造 で詳しく
    バイナリファイルbinary file
    独自の形式でデータを詰め込んだファイル。実行プログラム、画像、圧縮ファイル、Luantiのmap.sqliteなどが該当し、対応するプログラムでないと中身を解釈できない。第2章 ファイルシステムとディレクトリ構造 で詳しく
    シンボリックリンクln -s
    別のファイルやディレクトリを指す「ショートカット」。ln -s 実体 リンク名 で作る。ls -l で リンク名 -> 実体 と表示される。第2章 ファイルシステムとディレクトリ構造 で詳しく
    FHSFilesystem Hierarchy Standard
    Linuxのディレクトリ構成を定めた標準。どのディストリビューションでも、設定は/etc、ログは/var/logというように置き場所が共通になる。第2章 ファイルシステムとディレクトリ構造 で詳しく
    絶対パスabsolute path
    ルートディレクトリ「/」から書いた道順。/home/taro/backup のように、どこで実行しても同じ場所を指す。スクリプトやcronには必ずこちらを書く。第2章 ファイルシステムとディレクトリ構造 で詳しく
    相対パスrelative path
    いまいる場所（カレントディレクトリ）から見た道順。../world のように短く書けるが、実行時の居場所によって指す先が変わる。第2章 ファイルシステムとディレクトリ構造 で詳しく
    リンク数link count
    ls -l の第2列。同じ実体を指す名前（ハードリンク）の数で、ディレクトリでは . と .. の分も数えられるため2から始まる。中のファイル数ではない。第2章 ファイルシステムとディレクトリ構造 で詳しく
    inodeアイノード
    ファイルの中身ではなく、サイズ・所有者・権限・日時・データの置き場所を記録した管理票。ファイル名はこの番号への参照にすぎない。数には上限があり、小さなファイルを大量に作ると容量が余っていても No space left on device になることがある。第2章 ファイルシステムとディレクトリ構造 で詳しく
    アーカイブtar / .tar.gz
    複数のファイルを1つのファイルにまとめたもの。tar で作り、z を付ければgzip圧縮も同時に行われて .tar.gz になる。まとめる操作と小さくする操作は本来別のものである。第2章 ファイルシステムとディレクトリ構造 で詳しく
    差分コピーrsync
    転送元と転送先を比べ、違う部分だけを送る方式。2回目以降が非常に速いため日次バックアップに向く。--delete を付けると転送先を転送元の完全な鏡にするが、消し過ぎの事故が起きやすい。第2章 ファイルシステムとディレクトリ構造 で詳しく

    第3章 シェルとコマンドライン

    ターミナルterminal
    文字を入出力するための窓口となる画面。実習でBYODからsshして開くのも、この窓口である（第1回 1-3）。第3章 シェルとコマンドライン で詳しく
    シェルshell / bash
    入力されたコマンドを解釈し、カーネルに実行を依頼するプログラム。人間とカーネルの間に立つ通訳にあたる。実習の標準はbashである。第3章 シェルとコマンドライン で詳しく
    PATH環境変数
    シェルがコマンドの実体を探すディレクトリのリスト。コロン区切りで、先頭から順に探される。echo $PATH で内容、which ls で実際に選ばれる実体を確認できる。第3章 シェルとコマンドライン で詳しく
    環境変数environment variable
    シェルとその配下のプログラムが参照する設定値。echo $変数名 で確認し、export 変数名=値 で変更する。変更はそのシェルを閉じると消える。第3章 シェルとコマンドライン で詳しく
    標準エラー出力stderr（番号2）
    エラーメッセージが流れる出口。標準出力（番号1）とは別の配管なので、> でファイルに送っただけではエラーは記録されない。両方まとめたいときは 2>&1 を付ける。第3章 シェルとコマンドライン で詳しく
    パイプ|
    あるコマンドの標準出力を、次のコマンドの標準入力に直結する記号。ls | wc -l のように、小さな道具をつないで複雑な処理を組み立てられる。第3章 シェルとコマンドライン で詳しく
    クォートquoting
    シェルによる展開をどこまで許すかを決める引用符。シングルクォートは中身を完全に文字どおり扱い、ダブルクォートは $変数 とコマンド置換だけを展開する。空白を含むファイル名を1つの引数にまとめる役割もある。第3章 シェルとコマンドライン で詳しく
    終了コードexit status / $?
    コマンドが終わるときに残す0から255の数値。0が成功、0以外が失敗を表す。直前の値は echo $? で読め、&& （成功なら次へ）と || （失敗なら次へ）の判断材料になる。第3章 シェルとコマンドライン で詳しく
    正規表現regular expression
    文字列の形を表す記法。^ は行頭、$ は行末、. は任意の1文字を表す。grep -v '^#' のように「コメント行を除く」といった指定ができる。第3章 シェルとコマンドライン で詳しく
    SIGHUPhangup / nohup
    端末が切断されたときに、その端末で動いていたプロセスへ送られるシグナル。既定ではこれを受けて終了する。nohup を前に付けると無視させられるので、ログアウトしても処理が続く。第3章 シェルとコマンドライン で詳しく
    tmuxterminal multiplexer
    サーバ側に端末の作業画面を置いておける道具。Ctrl+B のあと d で切り離すと、SSHが切れても中の処理と画面が残り、tmux attach で同じ状態に戻れる。第3章 シェルとコマンドライン で詳しく

    第4章 テキストエディタ

    vi / Vimvi improved
    UNIX系OSの標準的なテキストエディタ。現在使われているのはほぼ改良版のVimで、実習で vi と打つと起動するのもVimである。第4章 テキストエディタ で詳しく
    POSIXportable operating system interface
    UNIX系OSが共通して備えるべき機能を定めた標準規格。viがここに含まれるため、どのサーバにも必ず入っていると期待できる。第4章 テキストエディタ で詳しく
    コマンドモードnormal mode
    viを起動した直後の状態。キーがそのまま編集命令として働く（xで1文字削除、ddで1行切り取りなど）。迷ったらEscを押せばここに戻る。第4章 テキストエディタ で詳しく
    入力モードinsert mode
    打ったキーがそのまま文字として入るモード。i／a／oで入り、Escで抜ける。画面下に -- INSERT -- と出ているのが目印である。第4章 テキストエディタ で詳しく
    vimtutorvimtutor ja
    Vimに付属する公式の練習用チュートリアル。約30分で基本操作をひととおり体験できる。フル版の vim パッケージに含まれる。第4章 テキストエディタ で詳しく
    ビジュアルモードvisual mode
    範囲を選んでからまとめて操作するためのモード。vで文字単位、Vで行単位に入り、移動キーで範囲を伸ばしてy（コピー）やd（削除）を押す。Escで抜ける。第4章 テキストエディタ で詳しく
    .vimrc~/.vimrc
    Vimの設定をまとめて書いておくファイル。ホームディレクトリに置くと起動時に自動で読み込まれ、set number などの設定を毎回打たずに済む。第4章 テキストエディタ で詳しく
    nanoGNU nano
    モードを持たない素直なテキストエディタ。開いたらすぐ入力でき、操作方法が画面下に常に出ている。^X の ^ はCtrlキーを意味する。第4章 テキストエディタ で詳しく
    diffdiff -u / unified形式
    2つのファイルの違いだけを表示するコマンド。-uを付けた形式では、-で始まる行が削除、+で始まる行が追加を表す。編集前のバックアップと見比べるのが定番の使い方である。第4章 テキストエディタ で詳しく
    構文チェックsystemd-analyze verify / sshd -t
    設定ファイルの書式だけを検査する機能。サービスを再起動する前に実行すると、起動失敗や締め出しの多くを未然に防げる。何も表示されないのが正常という点に注意する。第4章 テキストエディタ で詳しく

    第5章 ユーザ・グループとパーミッション

    UID・GIDUser ID / Group ID
    ユーザとグループに割り当てられる一意の番号。Linuxが権限を判断するときに見ているのは、画面に表示される名前ではなくこの番号である。第5章 ユーザ・グループとパーミッション で詳しく
    rootUID 0
    すべての権限チェックを免除される管理者ユーザ。できないことがない代わりに、打ち間違い1つでシステムを壊せる。第5章 ユーザ・グループとパーミッション で詳しく
    sudosuperuser do
    1つのコマンドだけを管理者権限で実行するための道具。普段は一般ユーザのまま作業し、必要なときだけ権限を借りる、という運用を可能にする。第5章 ユーザ・グループとパーミッション で詳しく
    最小権限の原則least privilege
    目的に必要な最小限の権限だけを与えるという設計指針。サービス専用ユーザを作る、鍵ファイルを本人だけに読ませる、といった具体策はすべてこの原則の表れである。第5章 ユーザ・グループとパーミッション で詳しく
    パーミッションpermission / rwx
    ファイルやディレクトリに設定されたアクセス権。所有者・所有グループ・その他の3者について、r（4）・w（2）・x（1）の組み合わせを3桁の数字で表す。第5章 ユーザ・グループとパーミッション で詳しく
    スティッキービットsticky bit / t
    /tmp のような誰でも書ける共有ディレクトリに付ける特殊な権限。全員がファイルを作れる一方、削除できるのは作った本人（と所有者・root）だけになる。第5章 ユーザ・グループとパーミッション で詳しく
    サービスアカウントservice account
    人間がログインするためではなく、特定のサービスを動かすために作るユーザ。実習のluantiユーザがこれにあたる。乗っ取られたときの被害をそのサービスの範囲に閉じ込めるために用意する。第5章 ユーザ・グループとパーミッション で詳しく
    sudoers/etc/sudoers
    誰がどのコマンドをsudoで実行できるかを定めた設定ファイル。書式を誤るとsudoが一切使えなくなるため、必ず visudo 経由で編集する。第5章 ユーザ・グループとパーミッション で詳しく
    umaskuser file creation mask
    これから作られるファイルやディレクトリから取り除く権限を決める設定。標準の 0022 では、ファイルは 644、ディレクトリは 755 で作られる。既存のファイルには影響しない。第5章 ユーザ・グループとパーミッション で詳しく
    setuidsetuid bit / rwsr-xr-x
    実行中だけファイルの所有者の権限で動くようにする特殊な権限。ls -l で s と表示される。passwd や sudo がこれにより動いている。第5章 ユーザ・グループとパーミッション で詳しく
    攻撃面attack surface
    外部から触れられる入口の総量。動いているサービス、開いているポート、インストールされたソフトの数だけ攻撃面は広がる。使わないものを減らすことが、そのまま防御になる。第5章 ユーザ・グループとパーミッション で詳しく
    多層防御defense in depth
    性質の異なる対策を重ねて、1つ破られても被害が広がらないようにする考え方。ファイアウォール、公開鍵認証、専用ユーザ、fail2banはそれぞれ別の層にあたる。第5章 ユーザ・グループとパーミッション で詳しく
    公開鍵認証public key authentication
    手元に秘密鍵、サーバに公開鍵を置き、パスワードを送らずに本人確認を行う方式。秘密鍵はパーミッション 600 で厳重に守り、絶対に他人に渡さない。第5章 ユーザ・グループとパーミッション で詳しく
    fail2banfail2ban-client
    認証の失敗ログを監視し、短時間に失敗を繰り返すIPアドレスを一時的に遮断するソフト。総当たり攻撃を現実的でなくする、多層防御の一層である。第5章 ユーザ・グループとパーミッション で詳しく

    第6章 プロセスとサービス管理

    プロセスprocess / PID
    実行中のプログラム1つ分の実体。起動ごとに一意の番号（PID）が付き、ps や kill ではこの番号で相手を指定する。第6章 プロセスとサービス管理 で詳しく
    シグナルsignal / SIGTERM・SIGKILL
    プロセスに送る短い通知。SIGTERMは「片付けて終了してほしい」という依頼、SIGKILLは問答無用の強制終了で、後者はプログラムに保存の機会を与えない。第6章 プロセスとサービス管理 で詳しく
    systemdPID 1 / systemctl
    Linuxの起動直後から最後まで動き続け、すべてのサービスの起動・停止・再起動・自動起動を管理する仕組み。操作の窓口が systemctl コマンドである。第6章 プロセスとサービス管理 で詳しく
    ユニットファイルunit file / .service
    「どのコマンドを、どのユーザで、いつ起動するか」を書いたサービスの定義ファイル。/etc/systemd/system/ に置き、編集したら systemctl daemon-reload で読み直させる。第6章 プロセスとサービス管理 で詳しく
    journaldjournalctl
    systemdが管理するサービスの出力を一元的に受け取って保存する仕組み。サービスが画面に出すはずだったメッセージは、すべて journalctl -u サービス名 で後から読める。第6章 プロセスとサービス管理 で詳しく
    load averageuptime / top
    CPUの順番待ちをしているプロセスの平均数。CPUコア数（Raspberry Pi 400は4）が目安で、これを超え続けていれば処理が追いついていない。第6章 プロセスとサービス管理 で詳しく
    nice値nice / renice
    プロセスのCPU優先度を表す -20 から 19 の数値。大きいほど他に譲る。重いバッチ処理に nice -n 10 を付けると、本命のサービスの応答を守りやすい。第6章 プロセスとサービス管理 で詳しく
    ドロップイン設定drop-in / override.conf
    ユニットファイル本体を書き換えずに、一部の項目だけを上書きする仕組み。systemctl edit で作られ、パッケージ更新で自分の変更が消えないという利点がある。第6章 プロセスとサービス管理 で詳しく
    ログの優先度priority / -p err
    ログの重要度を示す段階（emerg、alert、crit、err、warning、notice、info、debug）。journalctl -p err のように指定すると、その段階以上だけを取り出せる。第6章 プロセスとサービス管理 で詳しく
    systemd timer.timer / OnCalendar
    決まった時刻や間隔でサービスを起動するsystemdの仕組み。cronの代わりに使え、実行結果がjournaldに残り、systemctl list-timers で次回実行時刻を確認できる。第6章 プロセスとサービス管理 で詳しく

    第7章 ネットワークの基礎

    IPアドレスIP address
    ネットワーク上の機器を識別する番号。10.20.30.41 のように4つの数値で表す。実習で使う 10.x.x.x などはプライベートアドレスで、組織の外からは直接届かない。第7章 ネットワークの基礎 で詳しく
    DHCPDynamic Host Configuration Protocol
    IPアドレスを機器に自動で貸し出す仕組み。実習環境もこれなので、サーバのIPアドレスは電源を入れ直すと変わることがある。第7章 ネットワークの基礎 で詳しく
    mDNSmulticast DNS / .local
    DNSサーバを使わず、同じLANの中に呼びかけて名前からIPアドレスを調べる仕組み。「ホスト名.local」で接続できるのはこれのおかげで、サーバ側ではavahiが応答している。第7章 ネットワークの基礎 で詳しく
    ポート番号port
    1台の機器の中で、どのサービス宛ての通信かを区別する番号。SSHは22番、Luantiは30000番を使う。開いているポートは外部からの入口でもある。第7章 ネットワークの基礎 で詳しく
    ファイアウォールufw
    ポート単位で通信を通すか遮断するかを決める仕組み。「まず全部閉じて、必要な分だけ開ける」（デフォルト拒否）が設計の基本である。第7章 ネットワークの基礎 で詳しく
    DNSDomain Name System
    ドメイン名とIPアドレスを対応づける、世界中に分散した階層型のデータベース。手元の端末は代理のDNSサーバに問い合わせ、そのサーバが上位をたどって答えを集めてくる。第7章 ネットワークの基礎 で詳しく
    サブネットマスクsubnet mask / prefix
    IPアドレスのうち、どこまでが同じネットワークを指す部分かを決める指定。/24 なら先頭3つの数値が同じ相手には直接、違う相手にはルータ経由で届ける。第7章 ネットワークの基礎 で詳しく
    デフォルトゲートウェイdefault gateway
    同じネットワークにいない相手へパケットを託す出口のルータ。ip r の default via の行がこれで、この行が無いと外部のどこにも出られない。第7章 ネットワークの基礎 で詳しく
    NATNetwork Address Translation
    プライベートアドレスをルータのグローバルアドレスに書き換えて外部と通信させる仕組み。内側から始めた通信しか戻り道が分からないため、外から中への接続は既定では届かない。第7章 ネットワークの基礎 で詳しく
    ステータスコードHTTP status code
    HTTPの応答の1行目に付く3桁の番号。200番台は成功、300番台は移動、400番台は要求側の誤り、500番台はサーバ側の障害を表す。第7章 ネットワークの基礎 で詳しく
    TLSTransport Layer Security / HTTPS
    通信を暗号化し、改ざんを検知し、接続先のドメインを証明書で確認する仕組み。HTTPをこれで包んだものがHTTPSである。守るのは通信路であって、サーバの中身の安全ではない。第7章 ネットワークの基礎 で詳しく

    第8章 サーバ運用の基礎

    logrotatelog rotation
    ログファイルを一定期間・一定サイズごとに新しいものへ切り替え、古い世代を圧縮・削除する仕組み。これがないとログは増え続け、いつかディスクを埋める。第8章 サーバ運用の基礎 で詳しく
    NTPNetwork Time Protocol
    ネットワーク越しに正確な時刻をもらって時計を合わせる仕組み。ログの時刻も、cronが動く時刻も、これが合っていることが前提になっている。第8章 サーバ運用の基礎 で詳しく
    croncrontab
    指定した日時にコマンドを自動実行する仕組み。設定は crontab -e で編集し、「分 時 日 月 曜日 コマンド」の形で1行ずつ書く。第8章 サーバ運用の基礎 で詳しく
    3-2-1ルール3-2-1 rule
    バックアップの指針。3つのコピーを、2種類の媒体に持ち、うち1つは別の場所に置く。同じSDカードの中に何世代置いても、カードが壊れれば同時に失われる。第8章 サーバ運用の基礎 で詳しく
    世代管理generation / rotation
    バックアップを1つで上書きせず、日付ごとに複数残し、古いものから消していく運用。「壊れたことに数日後に気づいた」場合でも、壊れる前の状態に戻せる。第8章 サーバ運用の基礎 で詳しく
    死活監視alive monitoring
    サービスが動いているかどうかだけを繰り返し確かめる、最も基本的な監視。systemctl status や ping の結果を定期的に記録するだけでも成立する。第8章 サーバ運用の基礎 で詳しく
    増分バックアップincremental backup
    前回の取得から変わった分だけを保存する方式。容量は小さく済むが、復元にはフルとその後の増分をすべて順に戻す必要があり、1つでも欠けると復元できない。第8章 サーバ運用の基礎 で詳しく
    しきい値threshold
    これを超えたら異常とみなす境界の値。平常時の値を先に知らないと決められない。厳しすぎると通知が多すぎて無視され、緩すぎると手遅れになる。第8章 サーバ運用の基礎 で詳しく
    切り分けisolation
    障害の原因がどこにあるかを、範囲を狭めながら特定していく作業。自分側、経路、相手側の順に確かめるのが基本で、思いつきで試すより早く確実である。第8章 サーバ運用の基礎 で詳しく
    ポストモーテムpostmortem
    障害が収まった後に、何が起きて、どう直して、次にどう防ぐかをまとめる文書。人を責めるのではなく仕組みを直すことを目的とする。第8章 サーバ運用の基礎 で詳しく

    第9章 シェルスクリプト入門

    シェルスクリプトshell script
    シェルに打ち込むコマンドを順に並べたテキストファイル。新しい言語を覚えるのではなく、普段のコマンドをそのまま書けばよい。第9章 シェルスクリプト入門 で詳しく
    シバンshebang / #!
    スクリプトの1行目に書く #!/bin/bash のこと。どのプログラムでこのファイルを解釈するかをカーネルに伝える。第9章 シェルスクリプト入門 で詳しく
    コマンド置換$(コマンド)
    コマンドの実行結果を、その場の文字列として埋め込む書き方。DATE=$(date +%Y%m%d) のように、実行時の日付をファイル名に入れるときに使う。第9章 シェルスクリプト入門 で詳しく
    set -eu
    スクリプト冒頭に書く安全装置。-e はコマンドが失敗した時点で実行を止め、-u は未定義の変数の参照をエラーにする。第9章 シェルスクリプト入門 で詳しく
    bash -x
    スクリプトを実行しながら、各行と変数の展開結果を表示するトレース実行。どの行まで進み、変数に何が入っているかを直接目で見るための第一の道具。第9章 シェルスクリプト入門 で詳しく
    パラメータ展開parameter expansion
    ${VAR:-既定値} のように、変数の値を取り出すときに既定値や検査を同時に行う書き方。設定漏れのまま処理が進む事故を、1行で防げる。第9章 シェルスクリプト入門 で詳しく
    traptrap 処理 EXIT
    スクリプトが終了するときや、中断（Ctrl+C）を受け取ったときに実行する後始末を登録する組み込みコマンド。一時ファイルの削除を書いておけば、途中で失敗してもゴミが残らない。第9章 シェルスクリプト入門 で詳しく
    ヒアドキュメントhere document / <<EOF
    複数行のテキストをその場でコマンドの入力やファイルの中身として与える書き方。区切り語を <<'EOF' のように引用符で囲むと、中の $ が展開されない。第9章 シェルスクリプト入門 で詳しく
    shellcheck静的検査
    シェルスクリプトを実行せずに読んで、引用符の付け忘れなど定番のミスを指摘するツール。sudo apt install -y shellcheck で導入でき、指摘には SC2086 のような番号が付く。第9章 シェルスクリプト入門 で詳しく

    第10章 仮想化とコンテナ

    コンテナcontainer
    ホストOSのカーネルを共有したまま、ファイルシステムやネットワークなどの見える範囲を区切って動かすプロセス。ゲストOSを持たない分だけ軽い。第10章 仮想化とコンテナ で詳しく
    イメージimage
    アプリケーションと依存物一式を固めた読み取り専用のひな型。1つのイメージから何個でもコンテナを起動できる。第10章 仮想化とコンテナ で詳しく
    ボリュームvolume / バインドマウント
    コンテナの中の特定のパスを、ホスト側のディレクトリに対応付ける仕組み。実習の ./data のようにホストのパスを直接指定する形をバインドマウントと呼ぶ。第10章 仮想化とコンテナ で詳しく
    compose.yaml
    複数のコンテナの構成（イメージ、ポート、ボリューム、環境変数）を1つのファイルに宣言的に書いたもの。docker compose up -d でその状態を実現する。第10章 仮想化とコンテナ で詳しく
    Infrastructure as CodeIaC
    サーバやネットワークの構成を手順ではなくコードとして記述し、バージョン管理して何度でも同じ環境を再現する考え方。compose.yamlはその入門である。第10章 仮想化とコンテナ で詳しく
    ポートの公開publish / -p ホスト:コンテナ
    コンテナ内のポートを、ホストのポートに結び付けて外から届くようにする設定。書かなければコンテナはホストの外から一切見えない。既定はTCPで、UDPを使うサービスは 30000:30000/udp のように明示する。第10章 仮想化とコンテナ で詳しく
    Dockerfile
    イメージの作り方を1行ずつ書いた設計図。FROM で土台を選び、RUN や COPY で中身を積み、docker build -t 名前:タグ . でイメージにする。第10章 仮想化とコンテナ で詳しく
    レジストリregistry / Docker Hub
    イメージを保管して配布する場所。nginx:alpine のようにレジストリ名を省くとDocker Hubが使われ、lscr.io/linuxserver/luanti は lscr.io というレジストリを明示した書き方である。第10章 仮想化とコンテナ で詳しく
    AnsiblePlaybook / 冪等性
    SSH経由でサーバをあるべき状態にそろえる構成管理ツール。YAMLで書いた手順書をPlaybookと呼び、同じものを何度流しても結果が変わらないこと（冪等性）を目標に書く。第10章 仮想化とコンテナ で詳しく
    セキュリティグループsecurity group
    クラウド事業者が提供する、仮想サーバの手前に置かれるファイアウォール。サーバ内の ufw とは別物なので、両方で許可しないと通信は通らない。第10章 仮想化とコンテナ で詳しく

    第11章 Luantiサーバの技術

    クライアント／サーバモデルclient-server model
    状態と判定を1か所（サーバ）に集め、利用者側の端末（クライアント）は操作の送信と表示に徹する構成。あなたが管理するPiがサーバ、BYODのLuantiがクライアントである。第11章 Luantiサーバの技術 で詳しく
    マップブロックmapblock
    ワールドを管理する単位となる16×16×16の立方体。プレイヤーの周囲のブロックだけが読み込まれ、未踏の地では新しく生成されるため負荷が高くなる。第11章 Luantiサーバの技術 で詳しく
    privsprivileges / 権限
    プレイヤーごとに与えられる、サーバ内でできることの一覧。ゲーム内チャットから /privs で確認し、/grant・/revoke で付け外しする。Linuxのグループと権限にあたる。第11章 Luantiサーバの技術 で詳しく
    SQLite
    1つのファイルがそのままデータベースになる軽量なデータベース。Luantiの map.sqlite・auth.sqlite がこれで、サーバ稼働中は常に書き込まれている。第11章 Luantiサーバの技術 で詳しく
    Modmodification
    Luaで書かれたLuantiの拡張機能。アイテムやチャットコマンドを追加できるが、サーバ上で動くプログラムそのものなので、出所の確認が必要である。第11章 Luantiサーバの技術 で詳しく
    server_announce公開サーバ一覧への登録
    Luantiの公開サーバ一覧に自分のサーバを登録するかどうかの設定。既定は false で、本実習では絶対に true にしてはならない。第11章 Luantiサーバの技術 で詳しく
    default_privs新規プレイヤーの初期権限
    初めて接続したプレイヤーに自動で与えられる権限の一覧。既定は interact, shout（建築とチャット）で、見学だけさせたいなら default_privs = shout のように絞る。最小権限の原則をLuantiで実践する場所である。第11章 Luantiサーバの技術 で詳しく
    active_block_rangeアクティブブロック範囲
    プレイヤーの周囲でモンスターや装置を動かし続けるマップブロックの範囲。広いほど世界が生き生きする代わりにCPUを食う。Raspberry Piでラグが出るときに最初に下げる値である。第11章 Luantiサーバの技術 で詳しく
    world.mt
    ワールドごとの設定ファイル。使用するゲームのIDや、load_mod_名前 = true の行によるModの有効化がここに書かれる。ワールドディレクトリの中で最も小さいが、これが無いとワールドとして開けない。第11章 Luantiサーバの技術 で詳しく
