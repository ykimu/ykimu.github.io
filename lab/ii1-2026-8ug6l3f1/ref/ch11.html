    11.1クライアント／サーバモデル

    Luantiのマルチプレイは、典型的なクライアント／サーバ型のネットワークアプリケーションである。ワールドの状態（地形、持ち物、モンスターの位置）はすべてサーバが一元管理し、各プレイヤーのクライアントは「操作を送り、周辺の状態を受け取って描画する」ことに徹する。

    チートが難しいのは判定をサーバが握っているからであり、サーバが停止すれば全員が遊べなくなるのは状態がサーバに集中しているからである。この構図はオンラインゲーム全般はもちろん、Webサービス（ブラウザ＝クライアント、Webサーバ＝サーバ）とも同じである。

    クライアント／サーバモデルclient-server model
    状態と判定を1か所（サーバ）に集め、利用者側の端末（クライアント）は操作の送信と表示に徹する構成。あなたが管理するPiがサーバ、BYODのLuantiがクライアントである。

    11.2Luantiというソフトウェア

    Luantiは2010年に「Minetest」の名で公開され、2024年に現在の名前に改名された、オープンソースのボクセルゲームエンジンである。性能が重要な中核部分はC++で書かれ、ゲームのルールやアイテムはLuaというスクリプト言語で記述される。最大の特徴はエンジンとゲームの分離で、同じLuantiエンジンの上で「Minetest Game」（実習で使用）をはじめとする様々なゲームを動かせる。ゲームやMod（拡張機能）は公式のContentDB（content.luanti.org）で配布されている。

    オープンソース（LGPLライセンス）であることの意味は実習で体感したとおりである。クライアントは誰でも無料で入手でき、サーバも自由に立てられる。全員が自分のBYODから当たり前のように接続できたのは、このライセンスのおかげである。また、C++製で軽量なため、Javaで動く同種のゲームサーバと比べてメモリ・CPU消費が小さく、Raspberry Piのような小型機に向いている。

    11.3サーバの仕組みと負荷

    Luantiサーバは30000番ポート（UDP）で独自プロトコルの通信を待ち受ける。位置情報のような高頻度・小サイズのデータをやりとりするため、確実さのTCPではなく速度のUDPが選ばれている（第7章）。サーバは約0.1秒ごとに世界全体の状態を更新しており、この周期に処理が間に合わなくなると、操作への反応が遅れる「ラグ」として体感される。

    ワールドは16×16×16ブロックの立方体（マップブロック）単位で管理され、プレイヤーの周囲のブロックだけが読み込まれて動作する（active_block_range 等の設定で範囲を調整できる）。未踏の地への移動が最も重いのは、マップブロックの新規生成（地形計算）が走るからである。第3回の負荷実験で見たload averageの上昇とゲームのラグは、この処理がCPUを食い尽くしていく過程を、OS側とゲーム側の2つの窓から見ていたことになる。max_users（最大接続数）は、この負荷をサーバの性能に収めるための設計値である。

    マップブロックmapblock
    ワールドを管理する単位となる16×16×16の立方体。プレイヤーの周囲のブロックだけが読み込まれ、未踏の地では新しく生成されるため負荷が高くなる。
    よくある誤解・トラブル ゲームが重いのは、サーバのメモリが足りないからだ

    原因は多くの場合CPUである。未踏の地の地形生成が約0.1秒ごとの更新周期に間に合わなくなることでラグが生じる。top とload average（8.5節）で、どの資源が足りていないかを先に確かめる。

    11.4アカウントと権限（privs）

    Luantiのアカウントはサーバごとに独立している。中央の認証サーバは存在せず、プレイヤーが初回接続時に入力した名前とパスワードが、そのサーバのワールド内（auth.sqlite）にパスワードのハッシュとして登録される（第5章で学んだ /etc/shadow とまったく同じ発想である）。

    プレイヤーの行動は privs（権限）で制御され、interact（ブロックの設置・破壊）、shout（チャット）、give（アイテム入手）、server（サーバ管理）などの権限を /grant・/revoke コマンドで付け外しする。なお /ban は名前ではなく、接続中のプレイヤーのIPアドレスを禁止するコマンドであり、オフラインの相手には使えない（アカウント単位の制限は権限の剥奪で行う）。luanti.conf の name に指定したプレイヤーは全権限を持つ管理者になる。

    privsprivileges / 権限
    プレイヤーごとに与えられる、サーバ内でできることの一覧。ゲーム内チャットから /privs で確認し、/grant・/revoke で付け外しする。Linuxのグループと権限にあたる。
    よくある誤解・トラブル アイテムが欲しいときは /giveme を使えばよい

    本実習の環境では /giveme に必要な権限が登録されておらず（unknown privilege）使えない。第3回 3-4 のとおり /grant で creative 権限を与え、クリエイティブモードのインベントリからアイテムを取り出す。

    /ban を使えば、その人のアカウントを追放できる

    /ban が禁止するのは接続中のプレイヤーのIPアドレスであり、オフラインの相手には使えない。アカウント単位で行動を制限したいときは、/revoke で interact や shout を取り上げる。

    この仕組みには実習で学んだセキュリティの原則がそのまま現れる。管理者名は「最初に登録した者勝ち」なので公開前に自分で登録する（なりすまし防止）。プレイヤーのパスワードはハッシュで保存されるとはいえサーバ管理者の手元に渡るので、他サービスとの使い回しは厳禁である。そして一般プレイヤーには必要最小限の権限だけを与える：最小権限の原則（第5章）である。

    11.5データと設定の構造

    ファイル／ディレクトリ内容
    luanti.confサーバの設定（server_name、max_users、name等）。キー = 値 形式のテキスト。コンテナ版（第5回）では data/main-config/minetest.conf がこれに相当する
    world/ワールド一式。バックアップ対象はこのディレクトリ
    world/map.sqlite地形データの本体。SQLiteというファイル型データベース
    world/auth.sqliteアカウント情報（パスワードはハッシュで保存）
    world/world.mtワールドごとの設定（使用するゲーム、有効なMod等）

    「設定はテキストファイル、変更したら再起動」というLinuxサーバの原則が、Luantiにもそのまま当てはまる。一方でワールドの実体はSQLiteデータベースであり、稼働中にファイルをコピーすると書き込み途中の不整合を含む可能性がある。第4回 4-1のバックアップで「確実なのは停止してから」としたのはこのためである。

    SQLite
    1つのファイルがそのままデータベースになる軽量なデータベース。Luantiの map.sqlite・auth.sqlite がこれで、サーバ稼働中は常に書き込まれている。
    よくある誤解・トラブル サーバを動かしたままワールドをコピーしても、ファイルさえあれば復元できる

    書き込みの途中でコピーしたSQLiteファイルは壊れていることがあり、しかも壊れているかどうかはコピーした時点では分からない。サービスを停止してから取るのが確実で、取ったバックアップは第4回 4-4のように実際に戻して確かめるまで「バックアップがある」とは言えない。

    設定を書き換えれば、その場でサーバに反映される

    luanti.conf は起動時に読まれるため、書き換えたあとサービスを再起動するまで反映されない（第2回 2-5、コンテナ版は docker compose restart game）。

    11.6Modとゲーム制作への入口

    LuantiのModはLuaで記述する。数十行のスクリプトで新しいアイテムやコマンドを追加でき、ワールドの worldmods ディレクトリに置くだけで読み込まれる。ContentDBには他者の作ったゲームやModが多数公開されており、導入はディレクトリに配置して world.mt で有効化するだけである。ただし、Modはサーバ上で動くプログラムそのものなので、出所の確認が必要である。第10章で学んだ「イメージの出所を確認する」と同じ注意が、ここでも当てはまる。最終課題（第6回 6-1）でMod導入・自作に挑戦する人は、公式ドキュメント（docs.luanti.org）のModding Bookから始めるとよい。

    Modmodification
    Luaで書かれたLuantiの拡張機能。アイテムやチャットコマンドを追加できるが、サーバ上で動くプログラムそのものなので、出所の確認が必要である。

    11.7ContentDBからのMod導入手順

    最終課題のテーマ「Mod・ゲーム運用」の出発点となる手順を示す。ModはContentDB（https://content.luanti.org/）からzipで入手し、サーバのmodsディレクトリに展開したうえで、ワールドごとに有効化する。第5回のコンテナ構成（~/game）では、Modもボリューム内に置く。これも「データは資産」の実践である。

    Modの導入（コンテナ版・第5回の構成）
    cd ~/game/data && mkdir -p mods && cd mods
wget ContentDBのDownloadリンクのURL
unzip ダウンロードしたファイル.zip
vi ../worlds/world/world.mt
load_mod_Mod名 = true　← この1行を追記して有効化
docker compose restart game

    ゲーム全体（実習で使っているMinetest Game以外のゲーム）を導入する場合は、mods ではなく data/games に展開し、compose.yaml の CLI_ARGS の --gameid を新しいゲームのIDに切り替える（実習の構成では minetest を指定している）。ワールドはゲームごとに互換性がないため、新しいワールド名を指定して生成し直すのが安全である。

    Note

    ※ Modには依存Modや対応バージョンがある。ContentDBの各ページで依存関係（Dependencies）を確認し、導入は1つずつ・直前にバックアップを取ってから行うこと。起動しなくなったら docker compose logs にModのエラーが出ている。

    11.8luanti.conf 主要設定リファレンス

    第2回 2-4で書いた luanti.conf には数行しか書かなかったが、Luantiの設定項目は数百ある。ここでは、学内でサーバを運用するうえで実際に触る価値のあるものだけを、目的別に並べる。書式は キー = 値 の1行1項目で、真偽値は true か false である。

    注意

    ※ 行の途中に # を書いてはいけない。max_users = 5 # 最大5人 と書くと、値が「5 # 最大5人」という壊れた文字列として読まれる。コメントは行頭の # から始まる独立した行にする（第2回 2-4のつまずきポイント）。

    サーバの見せ方と接続に関する設定

    キー意味例と既定値
    server_nameサーバ一覧やクライアントに表示される名前server_name = 24s1234のサーバ
    server_descriptionサーバの説明文。一覧に出す短い紹介server_description = 実習用サーバ
    motd接続したプレイヤーにチャットで表示される挨拶motd = ようこそ！
    max_users同時接続できる人数の上限。既定は15max_users = 5
    port待ち受けるUDPポート番号。既定は30000port = 30000
    bind_address待ち受けるアドレス。空なら全てのネットワーク側で待つbind_address = 0.0.0.0
    server_announce公開サーバ一覧に自分を登録するか。既定はfalseserver_announce = false（学内では必ずfalse）
    注意

    ※ server_announce = true にすると、サーバの情報が世界中に公開されるサーバ一覧に登録される。本実習のサーバは学内ネットワークに閉じており、外部への公開は2.4 ネットワーク利用上の注意で禁止されている。この項目は false のまま（または書かないまま）にしておくこと。

    server_announce公開サーバ一覧への登録
    Luantiの公開サーバ一覧に自分のサーバを登録するかどうかの設定。既定は false で、本実習では絶対に true にしてはならない。

    port を変更した場合は、ufwの許可（sudo ufw allow 30000/udp）と、第5回のコンテナ構成における ports の記述も同時に直す必要がある。設定ファイルだけを変えてもクライアントは届かない。3か所がそろって初めて通る、という点は第7章 7-5のファイアウォールの考え方そのものである。

    アカウントと権限に関する設定

    キー意味例と既定値
    name管理者にするプレイヤー名。この名前は全権限を持つname = 自分のプレイヤー名
    disallow_empty_password空パスワードでの登録を禁止する。既定はfalsedisallow_empty_password = true
    default_privs新規プレイヤーに自動で与える権限。既定は interact, shoutdefault_privs = interact, shout
    default_password新規登録時の既定パスワード。空なら本人が決める（通常は設定しない）
    enable_rollback_recording誰がどのブロックを変えたかを記録し、/rollback で戻せるようにする。既定はfalseenable_rollback_recording = false

    name の値は「そのサーバの管理者」を意味するだけで、アカウントを作るわけではない。実際にその名前で接続して登録した人が管理者になるので、サーバを他人に見せる前に自分で登録しておくこと（第3回 3-4）。

    default_privs新規プレイヤーの初期権限
    初めて接続したプレイヤーに自動で与えられる権限の一覧。既定は interact, shout（建築とチャット）で、見学だけさせたいなら default_privs = shout のように絞る。最小権限の原則をLuantiで実践する場所である。

    遊び方を決める設定

    キー意味例と既定値
    creative_modeサーバ全体をクリエイティブモードにする。既定はfalsecreative_mode = true
    enable_damageプレイヤーがダメージを受けるか。既定はtrueenable_damage = false
    enable_pvpプレイヤー同士の攻撃を許すか。既定はtrueenable_pvp = false
    enable_tntMinetest GameのTNTを有効にする（負荷実験で使う）enable_tnt = true
    time_speedゲーム内時間の進む速さ。既定は72（現実の1日が20分）time_speed = 0（時間を止める）
    fixed_map_seed地形生成の乱数の種。同じ値なら同じ地形が生成されるfixed_map_seed = 1234567

    fixed_map_seed は、新しくワールドを作るときにだけ効く。すでに生成された地形は map.sqlite に保存されているので、あとから変えても既存のワールドは変化しない。全員で同じ地形を使いたい場合や、第5回 5-5の再構築で「同じ世界がもう一度作れること」を示したい場合に使える。

    負荷に効く設定

    11.3節で述べたとおり、Luantiサーバの負荷の中心はマップブロックの生成と送信である。Raspberry Piで動かすときは、次の項目を小さめにすると体感が安定する。ただし小さくしすぎると見える範囲が狭くなるので、1つずつ変えて第3回 3-5の平常値と比べながら調整すること。

    キー意味例と既定値
    active_block_rangeプレイヤーの周囲で常時動かすマップブロックの範囲。既定は4active_block_range = 2
    max_block_send_distanceクライアントへ送るマップブロックの最大距離。既定は12max_block_send_distance = 8
    max_simultaneous_block_sends_per_client1人あたり同時に送るブロック数の上限max_simultaneous_block_sends_per_client = 16
    max_objects_per_block1ブロックに置ける物体の数の上限。増えすぎ対策max_objects_per_block = 64
    server_unload_unused_data_timeout使われなくなったデータをメモリから解放するまでの秒数server_unload_unused_data_timeout = 29
    max_users同時接続人数の上限。負荷設計としては最も効く1行max_users = 5
    active_block_rangeアクティブブロック範囲
    プレイヤーの周囲でモンスターや装置を動かし続けるマップブロックの範囲。広いほど世界が生き生きする代わりにCPUを食う。Raspberry Piでラグが出るときに最初に下げる値である。

    変更を反映させる

    luanti.conf は起動時に読み込まれる。編集しただけでは何も起こらないので、必ずサービスを再起動する。第2回のsystemd構成と第5回のコンテナ構成で手順が違う点に注意すること。

    設定変更から反映までの手順（systemd構成）
    sudo cp /home/luanti/server/luanti.conf /home/luanti/server/luanti.conf.bak # 先に控えを取る
sudo -u luanti vi /home/luanti/server/luanti.conf
sudo systemctl restart luanti
systemctl is-active luanti
active
journalctl -u luanti -n 20 --no-pager # 起動時のログで設定の読み込みを確認
    設定変更から反映までの手順（コンテナ構成）
    cp data/main-config/minetest.conf data/main-config/minetest.conf.bak
vi data/main-config/minetest.conf
docker compose restart game
docker compose logs --tail 30 game
    よくある誤解・トラブル 設定を書いたのに、ゲーム内の表示が変わらない

    原因は3つのどれかである。再起動していない、キーの綴りが違う（Luantiは知らないキーを黙って無視する）、あるいは行の途中にコメントを書いて値が壊れている。journalctl -u luanti -n 30 で起動時のログを読み、設定ファイルのパスが意図したものかを確かめる。

    コンテナ版でも luanti.conf という名前で置けばよい

    コンテナ版（linuxserver/luanti）が読むのは data/main-config/minetest.conf である。名前も場所も異なるので、第5回 5-3のとおりコピー時に名前を変える。

    11.9権限（privs）の一覧と運用

    11.4節で述べたとおり、プレイヤーができることはprivsで決まる。ここでは実際に使う権限を一覧にし、付け外しの運用をまとめる。Linuxのユーザとグループ（第5章）と同じく、「必要な人に、必要な権限だけを、必要な期間だけ」が原則である。

    権限できること運用の目安
    interactブロックの設置と破壊、物に触れる。ゲームの中心既定で全員に与える。取り上げれば見学専用になる
    shoutチャットで発言する既定で全員に与える。迷惑行為の一時的な抑止に剥奪する
    fly ／ fast ／ noclip飛行 ／ 高速移動 ／ ブロックをすり抜ける建築の補助として一時的に与える。通常は与えない
    creativeクリエイティブモードのインベントリを使う（Minetest Gameが提供）アイテムが必要なときに与える。第3回 3-4で使う
    give/give・/giveme でアイテムを直接出す本実習の環境では登録されていない（後述）
    teleport ／ bring自分が移動する ／ 他人を自分のところへ呼ぶ管理者のみ。イベントの整列などに使う
    settime/time でゲーム内の時刻を変える管理者のみ
    kick ／ ban接続を切る ／ 接続元を出入り禁止にする管理者のみ。行使したら必ず記録を残す
    password他人のパスワードを変更・消去する管理者のみ。取り扱いに最も注意が要る
    basic_privs ／ privsinteract と shout の付け外し ／ 全権限の付け外しbasic_privs を補助役に渡し、privs は自分だけが持つ
    protection_bypass他人が保護した領域でも操作できる管理者のみ。原則として使わない
    server ／ debugサーバの停止などの管理操作 ／ 詳細な内部情報の表示管理者のみ

    新規プレイヤーが最初に持つ権限は default_privs で決まる（既定は interact, shout）。公開直前の準備中や、見学者だけを入れたいときは default_privs = shout としておき、必要な人に /grant で interact を与える運用にすると安全である。

    権限の確認と付け外し（ゲーム内チャットで実行）
    /privs # 自分の権限を表示
/privs プレイヤー名 # 相手の権限を表示
/grant プレイヤー名 interact # 建築を許可
/grant プレイヤー名 fly, fast # 複数をまとめて付与（カンマ区切り）
/revoke プレイヤー名 fly # 剥奪
/grant プレイヤー名 creative # クリエイティブのインベントリを使えるようにする
/grantme fly # 自分に付与（privs 権限が要る）
/haspriv interact # その権限を持つ接続中のプレイヤーを一覧

    出力の読み方は単純で、/privs 相手の名前 はカンマ区切りの権限名を1行で返す。/grant や /revoke の前後で同じコマンドを打ち、一覧が変わったことを目で確かめるのが確実な確認方法である。権限のないコマンドを実行すると You don't have permission to run this command と返り、存在しない権限名を指定すると Unknown privilege と返る。どちらのメッセージが出たかで、原因が権限不足なのか綴り誤りなのかを切り分けられる。

    よくある誤解・トラブル アイテムが欲しいので /giveme を使う

    本実習の環境では /giveme に必要な権限が登録されておらず（unknown privilege）使えない。第3回 3-4のとおり /grant プレイヤー名 creative で権限を与え、クリエイティブモードのインベントリからアイテムを取り出すこと。サーバ全体をクリエイティブにしたいときは luanti.conf に creative_mode = true を書いて再起動してもよい。

    /grant したのに相手の画面で何も変わらない

    fly や fast は権限を与えただけでは効かず、相手がクライアント側の操作（飛行の切り替えなど）を行う必要がある。まず /privs 相手の名前 で権限が実際に付いたかを確認し、付いていれば操作方法の問題である。

    注意

    ※ 一般プレイヤーに privs、password、server、protection_bypass を与えてはならない。privs を持つ相手は自分自身に全権限を付与でき、管理者からその権限を取り上げることもできる。これはLinuxで一般ユーザをsudoグループに入れるのと同じ重みの操作である（第5章）。

    11.10ワールドの中身と保守

    11.5節の表をもう一段掘り下げる。ワールドディレクトリの中身を知っておくと、バックアップで何を残すべきか、壊れたときにどこを見るかが分かる。

    ワールドディレクトリの構成

    ワールドの中身を見る
    sudo ls -la /home/luanti/server/world
合計 2216
drwxr-xr-x 3 luanti luanti    4096  9月 19 14:02 .
drwxr-xr-x 4 luanti luanti    4096  9月 19 13:02 ..
-rw-r--r-- 1 luanti luanti   24576  9月 19 14:02 auth.sqlite
-rw-r--r-- 1 luanti luanti     102  9月 19 14:02 env_meta.txt
-rw-r--r-- 1 luanti luanti 2179072  9月 19 14:02 map.sqlite
drwxr-xr-x 2 luanti luanti    4096  9月 19 13:40 players
-rw-r--r-- 1 luanti luanti      86  9月 19 13:02 world.mt
    名前中身失うと何が起きるか
    world.mt使用するゲーム（gameid）、バックエンド、有効なModの一覧ワールドとして認識されなくなる
    map.sqlite地形とブロックの本体。最も大きくなるファイル建築物がすべて消える
    auth.sqliteアカウント名、パスワードのハッシュ、各人のprivs全員が再登録になり、権限もやり直しになる
    players/プレイヤーごとの位置、体力、持ち物持ち物と位置が初期化される
    env_meta.txtゲーム内時刻や経過日数などの環境情報時刻と日数が初期化される（影響は小さい）

    バックアップの対象は個々のファイルではなく、ワールドディレクトリ全体である。第4回 4-2のbackup.shが tar czf ... -C "$HOME/server" world とディレクトリごと固めているのはこのためで、map.sqlite だけを取っても権限も持ち物も戻らない。

    world.mt
    ワールドごとの設定ファイル。使用するゲームのIDや、load_mod_名前 = true の行によるModの有効化がここに書かれる。ワールドディレクトリの中で最も小さいが、これが無いとワールドとして開けない。

    安全なバックアップ手順

    SQLiteは稼働中も書き込まれ続けているため、サーバを動かしたままコピーすると、書き込み途中の不整合を含む可能性がある。確実なのは「止めて、取って、動かす」である。停止時間は数十秒で済む。

    停止して取るバックアップ（systemd構成）
    sudo systemctl stop luanti # 止める（終了時にワールドが保存される）
sudo -u luanti tar czf /home/luanti/backup/world_$(date +%Y%m%d_%H%M%S).tar.gz -C /home/luanti/server world
sudo systemctl start luanti # すぐ動かす
systemctl is-active luanti
active
ls -lh /home/luanti/backup | tail -n 3
-rw-r--r-- 1 luanti luanti 1.4M  9月 19 14:35 world_20260919_143512.tar.gz

    確認するのは2点である。is-active が active に戻っていること、そして出来上がったファイルのサイズが前回と比べて極端に小さくないことである。数キロバイトしかないバックアップは、対象を取り違えているか、途中で失敗している。第4回 4-4のとおり、実際に展開して起動できるところまで確かめて初めて「バックアップがある」と言える。

    Note

    ※ どうしても止めたくない場合は、sqlite3 の .backup コマンドを使うと稼働中でも整合性のあるコピーが取れる（sudo apt install -y sqlite3 が必要）。ただし players/ や world.mt は別途コピーする必要があり、手順が増える。実習の規模では停止して取るほうが確実である。発展の例は付録A.5 バックアップの高度化にある。

    ログの見方

    第2回 2-5のユニットファイルは --logfile "" を指定しており、Luantiが自前のファイルに書く代わりに、出力がそのままjournaldへ渡るようにしてある。したがってLuantiのログは journalctl で読む（6.2節）。

    Luantiのログを読む
    journalctl -u luanti -n 30 --no-pager # 直近30行
journalctl -u luanti -f # 接続や切断をリアルタイムで見る
journalctl -u luanti --since today | grep -i "joins game" # 今日の入室だけを抜き出す
Sep 19 14:05:11 mc-24s1234 luantiserver[812]: ACTION[Server]: taro [192.168.1.44] joins game.
Sep 19 14:31:02 mc-24s1234 luantiserver[812]: ACTION[Server]: taro leaves game. List of players:

    見るべきは行頭の分類である。ACTION は入退室やブロックの設置といった通常の出来事、WARNING は動作は続くが注意すべきこと、ERROR は失敗である。joins game の行にはプレイヤー名と接続元のIPアドレスが両方出るので、第3回 3-6 演習：ログ解析ではこの行を数えて利用状況を集計している。コンテナ構成では同じ内容が docker compose logs game に出る。

    注意

    ※ ログにはプレイヤー名とIPアドレスが記録される。これは個人に結び付きうる情報なので、技術記事や発表資料に貼るときは必ず伏せること（第6回 6-3 公開時の注意）。

    11.11管理チャットコマンド一覧

    管理コマンドはサーバのターミナルではなく、Luantiクライアントのチャット欄（Tキーで開く）に入力する。ここでは実習と運用で使うものを目的別にまとめる。すべて /help と /help コマンド名 で確認できるので、迷ったらまずそれを打てばよい。

    コマンドはたらき必要な権限
    /statusサーバのバージョン、稼働時間、接続中のプレイヤー一覧不要
    /help ／ /help all使えるコマンドの一覧と説明不要
    /privs [名前]権限の確認不要
    /grant 名前 権限 ／ /revoke権限の付与 ／ 剥奪privs（一部は basic_privs）
    /kick 名前 [理由]指定したプレイヤーの接続を切るkick
    /ban 名前 ／ /unban 名前またはIP接続中のプレイヤーのIPを出入り禁止 ／ 解除ban
    /teleport X,Y,Z ／ /teleport 名前座標へ移動 ／ 相手のところへ移動teleport
    /time 時:分ゲーム内の時刻を変える（/time 6:00 で朝）settime
    /set キー 値設定値をその場で変更する（永続化はされない）server
    /mods ／ /days読み込まれているModの一覧 ／ 経過日数不要
    /shutdown [秒] [再起動] [メッセージ]サーバを停止する。予告してから落とせるserver
    /clearobjects [full|quick]ワールド上の物体を削除する（後述の注意を必ず読むこと）server

    /shutdown 60 false 60秒後に再起動します のように書くと、メッセージを表示してから60秒後に停止する。全員を巻き込む操作なので、必ず予告してから実行すること。なお /shutdown で止めた場合、systemdの Restart=on-failure は正常終了とみなして再起動しない。作業後は sudo systemctl start luanti で自分で起動する。

    注意

    ※ /clearobjects は、ワールド上のアイテムや乗り物、Modが置いた物体をまとめて削除する。full を付けると読み込まれていない領域まで対象になり、ワールド全体を走査するためRaspberry Piでは数分間サーバが応答しなくなる。地面に落ちたアイテムが増えすぎて重い、といった明確な理由があるときだけ、バックアップを取り、プレイヤーに予告してから実行すること。取り消しはできない。

    実習ではここで使う

    ※ /status・/privs・/grant・/revoke・/ban・/unban は第3回 3-4 Luantiのプレイヤー管理で実際に打つ。/status の出力は第5回 5-4の監視ページに載せる情報の候補でもある。

    よくある誤解・トラブル コマンドを打っても Invalid command としか返ってこない

    先頭の / を忘れていないか、全角で入力していないかを確かめる。チャット欄では全角の「／」はコマンドとして認識されない。綴りが正しくても権限が無い場合は、別のメッセージ（権限が無い旨）が返る。

    /set で設定を変えたので、luanti.conf は直さなくてよい

    /set の変更は動作中のサーバにだけ効き、再起動すると luanti.conf の内容に戻る。恒久的に変えたいなら設定ファイルを直し、サービスを再起動すること（11.8 変更を反映させる）。
