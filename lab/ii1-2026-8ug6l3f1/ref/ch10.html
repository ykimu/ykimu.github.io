    10.1仮想化の2つの方式

    1台の物理マシンの上に複数の独立した実行環境を作る技術を仮想化という。方式は大きく2つある。仮想マシン型は、ハイパーバイザという仮想化ソフトの上に、ゲストOSを丸ごと含む仮想マシンを立てる。完全な分離が得られる反面、OSを1台分ずつ動かすためメモリもストレージも多く消費し、起動にも分単位の時間がかかる。

    コンテナ型は、ホストOSのカーネルを共有したまま、プロセスの見える世界（ファイルシステム、ネットワーク、プロセス一覧）だけを区切る。ゲストOSを持たないため軽量で、起動は秒単位、Raspberry Piのような小型機でも実用になる。

    コンテナcontainer
    ホストOSのカーネルを共有したまま、ファイルシステムやネットワークなどの見える範囲を区切って動かすプロセス。ゲストOSを持たない分だけ軽い。
    よくある誤解・トラブル コンテナは軽い仮想マシンなので、どんなOSでも中で動かせる

    コンテナはホストのカーネルをそのまま使う。したがってCPUの種類も共有され、Raspberry Pi（arm64）ではarm64に対応したイメージしか動かない。「イメージをpullできない」「exec format error」はここが原因のことが多い。

    10.2Dockerの基本概念

    Dockerを理解する鍵は、イメージとコンテナの区別である。イメージは「アプリケーションと依存物一式を固めた読み取り専用のひな型」、コンテナは「イメージから起動した実行中の実体」である。プログラムとプロセスの関係（第6章）とちょうど同じで、1つのイメージから何個でもコンテナを起動できる。イメージはDocker Hubなどのレジストリで共有されており、docker compose up しただけでlinuxserver/luantiのサーバが動いたのは、ビルド済みイメージをレジストリから取得（pull）したからである。

    イメージimage
    アプリケーションと依存物一式を固めた読み取り専用のひな型。1つのイメージから何個でもコンテナを起動できる。

    イメージはレイヤ（層）の重なりでできている。「OSの基本部分」＋「共通ライブラリ」＋「サーバ本体」のように差分を積み重ねる構造のため、共通部分は複数のイメージで共有され、ダウンロードもストレージも節約される。自分でレイヤを定義してイメージを作るための設計図がDockerfileである（最終課題の発展テーマ）。

    10.3データの扱い：ボリューム

    コンテナ内で書き込んだデータは、コンテナを削除すると一緒に消える。これは欠点ではなく「環境をいつでも作り直せる」ための設計であり、残したいデータだけをボリューム（ホスト側のディレクトリとの対応付け）としてコンテナの外に出す。

    実習（第5回 5-3）のcompose.yamlで ./data:/config/.minetest と書いたのは、「コンテナ内の /config/.minetest を、ホストの ./data に重ねる」という意味である。ワールドデータはホスト側に実体があるため、コンテナを何度作り直しても失われない。「環境は使い捨て、データは資産」というコンテナ運用の原則は、この仕組みに支えられている。

    ボリュームvolume / バインドマウント
    コンテナの中の特定のパスを、ホスト側のディレクトリに対応付ける仕組み。実習の ./data のようにホストのパスを直接指定する形をバインドマウントと呼ぶ。
    よくある誤解・トラブル コンテナの中に入って設定ファイルを直せば、それで設定変更は完了する

    その修正はコンテナを作り直した瞬間に消える。直すのはホスト側のファイル（ボリューム）か compose.yaml であり、そのうえでコンテナを作り直すのがコンテナ流の運用である。

    ボリュームの中のファイルが Permission denied で書けない

    ホスト側のファイルの所有者と、コンテナが使うPUID/PGIDが食い違っている。ls -ln data で数値のUID・GIDを確かめ、必要なら sudo chown -R 1000:1000 data でそろえる（第5章）。

    10.4ComposeとInfrastructure as Code

    docker compose は、複数コンテナの構成をcompose.yamlという1つのファイルに宣言的に記述し、一括で管理するツールである。「宣言的」とは、手順（どうやって作るか）ではなく、あるべき状態（何がどう動いているべきか）を書くという意味である。composeは現在の状態と記述を比較し、差分だけを適用する。第5回 5-4でwebサービスを追記して up し直したとき、gameコンテナは再起動されず、webだけが新規に起動されたのはこのためである。

    compose.yaml
    複数のコンテナの構成（イメージ、ポート、ボリューム、環境変数）を1つのファイルに宣言的に書いたもの。docker compose up -d でその状態を実現する。

    この「インフラの構成をコードとして記述し、バージョン管理し、何度でも同じ環境を再現する」という考え方をInfrastructure as Code（IaC）と呼ぶ。クラウド時代の運用の中心概念であり、compose.yamlはその入門である。

    設定ファイルさえ保存しておけば環境を捨てても再現できる、という感覚を第5回 5-5 の総合演習で体験したことは、TerraformやKubernetesといった実務のツール群を学ぶときの土台になる。

    Infrastructure as CodeIaC
    サーバやネットワークの構成を手順ではなくコードとして記述し、バージョン管理して何度でも同じ環境を再現する考え方。compose.yamlはその入門である。

    10.5コンテナ利用の注意点

    • イメージの出所を確認する。レジストリには誰でもイメージを公開できるため、公式イメージや実績のあるイメージ（linuxserver/luantiは後者の代表例）を選ぶ。
    • タグを意識する。イメージ名の後ろの :latest は「その時点の最新」であり、時間が経つと中身が変わる。再現性を重視する場面ではバージョンを固定する（例：nginx:1.27-alpine）。
    • コンテナも監視・更新の対象である。「動いているから放置」はホストのサーバと同様に危険で、イメージの更新（脆弱性修正）を定期的に取り込む運用が必要である。

    10.6Dockerの基本操作：コンテナのライフサイクル

    コンテナには「イメージの取得（pull）→作成→起動→停止→削除」というライフサイクルがある。docker run はこのうち取得（手元になければ）・作成・起動をまとめて実行する複合コマンドであり、実習（第5回 5-2）で最初に実行した docker run hello-world の出力には、まさにこの流れが説明されている。コンテナを削除（rm）してもイメージは手元に残るため、同じイメージから何度でも新しいコンテナを作り直せる。「環境は使い捨て、データは資産」という原則は、このライフサイクルに支えられている。

    コマンドはたらき
    docker run [オプション] イメージコンテナの作成と起動（イメージが無ければpullも行う）
    docker ps ／ docker ps -a実行中の一覧／停止中も含めた一覧。STATUS列に注目する
    docker stop ／ start 名前停止（後片付けの機会を与える）／再開
    docker rm 名前コンテナの削除。イメージとボリュームは残る
    docker images ／ docker rmi手元のイメージ一覧／イメージの削除
    docker logs -f 名前コンテナのログを表示（-f でリアルタイム追跡）
    docker exec -it 名前 bash稼働中のコンテナの中でシェルを開く

    docker run のオプションは、実習で書いた compose.yaml の各項目と1対1に対応している。次の例（nginx）を compose.yaml のweb サービスの定義と見比べてほしい。

    docker run の代表的なオプション
    docker run -d --name web -p 8080:80 -v $(pwd)/html:/usr/share/nginx/html:ro --restart unless-stopped nginx:alpine
-p 8080:80 はポート公開（ホスト側:コンテナ側）、-v はボリューム、--restart unless-stopped は自動再起動、nginx:alpine はイメージ名:タグ

    -d はバックグラウンド実行、-p はポートの公開、-v はボリューム（:ro を付けると読み取り専用）、--restart は自動再起動の方針である。つまり compose.yaml は、これらのオプションをファイルに書き下ろしたものにすぎない。composeが読めればrunコマンドも読めるし、その逆もまた然りである。イメージ名は「レジストリ/リポジトリ:タグ」で構成され、タグを省略すると :latest が使われる（10.5節で述べたとおり、再現性が必要な場面ではタグを固定する）。

    docker exec -it 名前 bash を使うと、稼働中のコンテナの中に入って調査できる。ただしコンテナの中身は必要最小限で、viすら入っていないことも多い。中に入って直接修正するのではなく、ホスト側のファイル（ボリューム）や compose.yaml を直してコンテナを作り直すのがコンテナ流の運用である。

    Note

    ※ docker stop は第6章の systemctl stop と同じ発想で、まず「終了してください」という丁寧な依頼（SIGTERM）を送り、応答がなければ強制終了する。ワールドの保存など後片付けの機会が与えられるため、docker kill（即時抹消）を常用してはいけない。

    10.7docker compose の操作

    composeのコマンドは「compose.yamlのあるディレクトリ」で実行するのが基本である（実習では ~/game）。重要な性質は差分適用であり、up は足りないものだけを作り、compose.yamlを編集した後の up -d は変更のあったサービスだけを作り直す。何かを変えるたびに全部を消して作り直す必要はない。

    コマンドはたらき
    docker compose up -d一式を起動。2回目以降は差分だけを作成・再作成する
    docker compose downコンテナとネットワークを削除（ボリュームは残る）
    docker compose psこのプロジェクトのコンテナ一覧と状態
    docker compose logs -f [サービス名]ログの表示。サービス名を省略すると全サービス分
    docker compose restart [サービス名]サービスの再起動（設定ファイル変更の反映など）
    docker compose pullイメージの更新を取得（適用は次の up -d で）
    docker compose exec サービス名 bash指定サービスのコンテナに入る
    docker compose configcompose.yamlの文法確認（起動せずに検証できる）
    イメージ更新の定番手順
    docker compose pull # 新しいイメージを取得
docker compose up -d # 更新があったサービスだけ再作成
docker compose ps # 状態を確認
docker compose logs -f game # 気になるサービスのログを追う
    Note

    ※ down はコンテナとネットワークだけを消し、./data のようなホスト側ディレクトリ（バインドマウント）には触れない。down -v は compose.yaml で宣言した名前付きボリュームと匿名ボリュームを削除するオプションで、実習のバインドマウントは消えないが、名前付きボリュームにデータを置く構成では取り返しがつかない。癖として不用意に -v を付けないこと（もちろん、ホスト側で rm -rf data とすればワールドは消える）。第8章のバックアップがあれば、こうした操作も恐れずに試せる。

    10.8コンテナのデバッグ

    コンテナの障害対応も、第8章で学んだ「エラーを読む→仮説を立てる→確認する」の繰り返しであり、入口はほぼ常にログである。まず docker ps -a のSTATUS列で「Exited (1)」のような終了コードを確認し、docker compose logs でエラーメッセージを読む。よくある症状と確認手順を挙げる。

    症状確認すること
    起動してもすぐ落ちるdocker ps -a で終了コード → logs でエラーを読む。設定の誤りかPUID/PGIDの不一致が定番
    port is already allocatedポートの先客がいる。ss -tlnp（UDPは -ulnp）で使用中のプロセスを探す
    Permission deniedボリュームの所有者とPUID/PGIDの不一致。sudo chown -R 1000:1000 data
    イメージをpullできないネットワーク疎通と、イメージがarm64（Raspberry Pi）に対応しているかを確認
    ディスクを圧迫しているdocker system df で内訳を確認 → docker system prune で未使用の資源を掃除

    リソースの監視には docker stats が使える。コンテナごとのCPU・メモリ使用量をリアルタイム表示する、第3回 3-5で使ったtopのコンテナ版である。「平常時の値を知っておく」という監視の基本（8.5節）は、コンテナになっても変わらない。

    よくある誤解・トラブル docker ps に出てこないので、そのコンテナは作られていない

    docker ps は実行中のものしか表示しない。起動直後に落ちたコンテナは docker ps -a に Exited として残っており、原因は docker compose logs に書かれている。まず一覧、次にログという順で見る。

    動かないので、とりあえず down して作り直せば直る

    設定が誤っていれば作り直しても同じ結果になる。ログを読んで原因を1つ特定してから compose.yaml を直すこと。なお docker compose config を使えば、起動せずに文法だけを検証できる。

    Note

    ※ docker system prune は「使われていないもの」を一括削除する強力なコマンドである。停止中のコンテナも削除対象になるため、実行前に docker ps -a で消えて困るものがないかを必ず確認すること。

    10.9docker コマンドリファレンス

    10.6節で主要なコマンドの一覧を示したが、実際に運用していると「いまどうなっているかを調べる」「ログを読む」「散らかったものを片付ける」という3つの場面で、もう少し細かいオプションが要る。ここではその実用範囲をまとめる。第5回の構成（~/game の下に compose.yaml、data、html がある状態）を前提に読んでほしい。

    いまの状態を調べる

    障害対応の第一歩は一覧である。docker ps は実行中のコンテナだけを表示するので、落ちたコンテナを探すときは必ず -a を付ける。イメージの一覧は docker images、ディスクの内訳は docker system df で見る。

    状態を調べる基本形
    docker ps # 実行中のコンテナ
docker ps -a # 停止中も含めた全部
docker ps -a --filter status=exited # 落ちたものだけに絞る
docker images # 手元のイメージ一覧
docker system df # 何がディスクを使っているか
docker inspect --format '{{.State.ExitCode}}' game-game-1 # 終了コードだけを取り出す
    オプション意味例
    -a停止中のコンテナも表示する。障害調査では必須docker ps -a
    --filter 条件状態や名前で絞り込む（status=exited、name=web）docker ps --filter name=web
    --format '{{.項目}}'必要な列だけを取り出す。スクリプトから使うときに便利docker ps --format '{{.Names}}'
    -qIDだけを出す。他のコマンドへ渡すために使うdocker ps -aq
    docker inspect 名前コンテナやイメージの設定をJSONで詳細表示するdocker inspect game-web-1
    docker statsコンテナごとのCPU・メモリをリアルタイム表示（topのコンテナ版）docker stats --no-stream

    出力の読み方

    docker ps -a の出力
    docker ps -a
CONTAINER ID   IMAGE                        COMMAND                   CREATED       STATUS                   PORTS                      NAMES
0f1c2d3e4a5b   lscr.io/linuxserver/luanti   "/init"                   2 hours ago   Up 2 hours               0.0.0.0:30000->30000/udp   game-game-1
7a8b9c0d1e2f   nginx:alpine                 "/docker-entrypoint.sh"   2 hours ago   Up 2 hours               0.0.0.0:8080->80/tcp       game-web-1
3c4d5e6f7a8b   hello-world                  "/hello"                  3 hours ago   Exited (0) 3 hours ago                              friendly_kepler

    見るべき列は3つである。STATUSが Up なら稼働中、Exited (0) は正常終了、Exited (1) や Exited (137) は異常終了で、括弧の中が終了コードである（137はSIGKILLで殺されたことを示す）。PORTSは ホスト側->コンテナ側 の対応で、ここに何も出ていないコンテナは外から接続できない。NAMESはcomposeが付けた名前で、「プロジェクト名（ディレクトリ名）とサービス名と連番」を - でつないだ形になる。以降のコマンドではこの名前を指定する。

    docker system df の出力
    docker system df
TYPE            TOTAL     ACTIVE    SIZE      RECLAIMABLE
Images          4         2         612.3MB   271.5MB (44%)
Containers      3         2         1.1MB     0B (0%)
Local Volumes   1         0         0B        0B
Build Cache     0         0         0B        0B

    RECLAIMABLE（回収可能）の列が、掃除で取り戻せる容量である。上の例ではイメージの271.5MBが使われていない分で、これは古いタグや、更新して置き換わった前のイメージが残っているためである。SDカードは容量が小さいので、この値が大きくなってきたら片付けどきである。

    docker run の主要オプション

    docker run は「イメージの取得（手元になければ）、コンテナの作成、起動」をまとめて行う複合コマンドである。実習ではcomposeを使うので直接打つ機会は少ないが、compose.yaml の各キーがこのオプションと1対1に対応しているため、両方を見比べておくと理解が早い。

    docker run の代表例
    docker run --rm hello-world # 動作確認。--rm で終了後に自動削除
docker run -d --name web -p 8080:80 -v "$PWD/html:/usr/share/nginx/html:ro" --restart unless-stopped nginx:alpine
docker run -d --name game -p 30000:30000/udp -v "$PWD/data:/config/.minetest" -e TZ=Asia/Tokyo lscr.io/linuxserver/luanti
docker run --rm -it debian:bookworm-slim bash # 使い捨てのシェルで試す
    オプション意味compose.yaml の対応キー
    -dバックグラウンドで実行する（付けないと端末が占有される）（up -d で指定）
    --name 名前コンテナに名前を付ける。付けないとランダムな名前になるcontainer_name（通常は不要）
    -p ホスト:コンテナポートを公開する。/udp を付けるとUDPports
    -v ホスト:コンテナ[:ro]ボリューム。:ro で読み取り専用volumes
    -e キー=値環境変数を渡す（TZ、PUID など）environment
    --restart 方針自動再起動。unless-stopped は手で止めた場合以外は再起動restart
    --rm終了したらコンテナを自動削除する（使い捨ての確認用）（composeでは使わない）
    -it端末をつないで対話的に操作する（bash を動かすとき）stdin_open / tty

    -p の左がホスト側、右がコンテナ側である。-p 8080:80 は「ホストの8080番に来た通信を、コンテナの80番へ渡す」という意味であり、左右を逆にすると当然つながらない。Luantiは -p 30000:30000/udp のように /udp が必須で、これを忘れるとTCPの30000番が開くだけでクライアントからは接続できない（第7章 7-4）。

    ポートの公開publish / -p ホスト:コンテナ
    コンテナ内のポートを、ホストのポートに結び付けて外から届くようにする設定。書かなければコンテナはホストの外から一切見えない。既定はTCPで、UDPを使うサービスは 30000:30000/udp のように明示する。

    ログを読む、中に入る

    コンテナの調査はログから始まる。コンテナが標準出力に書いたものはDockerが受け取って保持しており、docker logs でいつでも読める。systemdのサービスに対する journalctl -u（6.2節）とまったく同じ位置付けの道具である。

    ログと調査
    docker logs game-game-1 # 最初から全部
docker logs --tail 50 game-game-1 # 末尾50行だけ
docker logs -f --since 10m game-game-1 # 直近10分ぶんを追跡表示
docker exec -it game-web-1 sh # コンテナの中でシェルを開く（alpineはbashが無い）
docker exec game-web-1 ls /usr/share/nginx/html # 1コマンドだけ実行する
    オプション意味例
    -fリアルタイムに追跡する（止めるのは Ctrl+C）docker logs -f game-web-1
    --tail N末尾のN行だけ表示する。長いログの入口として使うdocker logs --tail 50 game-game-1
    --since 時間指定時間より新しいログだけ（10m、1h、日時指定も可）docker logs --since 1h game-game-1
    -t各行に時刻を付ける。いつ起きたかを特定したいときdocker logs -t --tail 20 game-web-1
    exec -it 名前 sh中でシェルを開く。軽量イメージには bash が無いことが多いdocker exec -it game-web-1 sh
    Note

    ※ docker logs -f を Ctrl+C で止めても、コンテナは動いたままである。止まるのは表示だけであり、ここは journalctl -f と同じ感覚でよい。

    よくある誤解・トラブル docker exec -it 名前 bash が OCI runtime exec failed で失敗する

    そのイメージに bash が入っていないだけである。alpine系の軽量イメージには sh しかないので docker exec -it 名前 sh とする。そもそもコンテナの中に入って直すのはコンテナ流ではなく、直す対象はホスト側のファイルか compose.yaml である（10.3節）。

    止める、消す、掃除する

    コンテナの停止と削除は別の操作である。stop は止めるだけで、docker ps -a には Exited として残る。完全に消すのが rm で、イメージを消すのは rmi である。散らかったものをまとめて片付けるのが system prune だが、これは強力なので実行前の確認が要る。

    停止と片付け
    docker stop game-web-1 # 終了依頼を送り、応答がなければ強制停止
docker start game-web-1 # 停止中のコンテナを再開
docker restart game-web-1 # 停止して起動
docker rm game-web-1 # コンテナの削除（イメージとボリュームは残る）
docker rmi nginx:alpine # イメージの削除（使用中なら拒否される）
docker container prune # 停止中のコンテナをまとめて削除
docker image prune # タグの付いていない不要イメージを削除
    注意

    ※ docker system prune -a は「いま使われていないイメージ」を全部消す。次に docker compose up -d したときに、消したイメージを回線から取り直すことになるため、学内ネットワークの状況によっては復旧に時間がかかる。実行前に必ず docker system df で回収量を確かめ、docker ps -a で消えて困るコンテナがないことを確認すること。--volumes を足すと名前付きボリュームまで消えるので、この実習では付けない。

    10.10docker compose リファレンス

    composeは、複数のコンテナの「あるべき状態」を1つのファイルに書いて一括で扱うための道具である。10.7節で操作の一覧を示したので、ここでは compose.yaml の書き方そのものを整理する。

    compose.yaml の主要キー

    トップレベルの services の下に、サービス名（第5回では game と web）を並べ、その中に設定を書く。インデントは半角スペースだけを使い、同じ階層は同じ桁にそろえる。

    キー意味実習での値
    services動かすコンテナの集合。この下に1つずつサービスを書くgame、web
    image使うイメージ。レジストリ/リポジトリ:タグ の形lscr.io/linuxserver/luanti、nginx:alpine
    ports公開するポート。"ホスト:コンテナ"、UDPは /udp を付ける"30000:30000/udp"、"8080:80"
    volumesホストとコンテナのディレクトリ対応。:ro で読み取り専用./data:/config/.minetest、./html:/usr/share/nginx/html:ro
    environmentコンテナに渡す環境変数PUID、PGID、TZ、CLI_ARGS
    restart自動再起動の方針。unless-stopped が実用的unless-stopped
    depends_on起動の順序。先に立ち上げたいサービスを指定する（実習では未使用）
    Note

    ※ depends_on が保証するのは「起動した順番」だけで、「相手が受け付けられる状態になったこと」ではない。データベースとアプリのように相手の準備完了を待ちたい場合は、アプリ側が接続に失敗したら再試行するように作るのが定石である。実習の game と web は互いに依存していないため、指定していない。

    実習の compose.yaml を通して読む

    第5回 5-3と5-4で書いた2つのサービスを、1枚にまとめた形が次である。ポートもボリュームも実習と同じ値であり、web は game と同じ深さ（2桁のインデント）に並ぶ。

    2サービス構成の compose.yaml（第5回の完成形）
    services:
  game:
    image: lscr.io/linuxserver/luanti
    environment:
      PUID: "1000"
      PGID: "1000"
      TZ: Asia/Tokyo
      CLI_ARGS: "--gameid minetest --worldname world"
    ports:
      - "30000:30000/udp"
    volumes:
      - ./data:/config/.minetest
    restart: unless-stopped
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./html:/usr/share/nginx/html:ro
    restart: unless-stopped

    読み方の勘所は3つである。第一に、ports と volumes は「ホスト側が左」で統一されている。第二に、./data と ./html の ./ は「compose.yaml のあるディレクトリから見た相対パス」であり、これを省くとホストのディレクトリではなくDockerが管理する名前付きボリュームになってしまう。第三に、web 側だけ :ro が付いている。Webサーバは配るだけで書き込む必要がないので、読み取り専用にして事故の範囲を狭めている。最小権限の原則（第5章）がここにも現れている。

    サブコマンドと出力の読み方

    composeのコマンドは compose.yaml のあるディレクトリで実行する。実習では cd ~/game してから打つ。編集したら、まず config で文法を確かめてから up -d するのが安全な順序である。

    編集から反映までの定番手順
    docker compose config # 文法と解釈結果の確認（起動しない）
docker compose up -d # 差分だけを作成・再作成して起動
docker compose ps # 状態の確認
docker compose logs -f web # 特定のサービスのログを追う
docker compose restart game # 設定ファイルの変更を反映させる
docker compose down # コンテナとネットワークを削除（./data と ./html は残る）

    出力の読み方

    docker compose ps の出力
    docker compose ps
NAME          IMAGE                        COMMAND                   SERVICE   CREATED       STATUS       PORTS
game-game-1   lscr.io/linuxserver/luanti   "/init"                   game      2 hours ago   Up 2 hours   0.0.0.0:30000->30000/udp
game-web-1    nginx:alpine                 "/docker-entrypoint.sh"   web       2 hours ago   Up 2 hours   0.0.0.0:8080->80/tcp

    SERVICE列が compose.yaml に書いたサービス名、NAME列がDockerが実際に付けたコンテナ名である。game- という接頭辞はプロジェクト名、すなわち compose.yaml を置いたディレクトリ名（~/game）から自動的に付く。したがって、別のディレクトリで同じ compose.yaml を使えば別のプロジェクトとして動く。PORTS列が空のサービスは外から接続できないので、つながらないときは最初にここを見る。STATUSが Up でなければ docker compose logs サービス名 に進む（10.8節）。

    実習ではここで使う

    ※ 実習で実際に打つのは第5回 5-3 Luantiサーバのコンテナ化と5-5 総合演習である。総合演習では、compose.yaml と data と html の3つさえあれば環境を作り直せることを確かめる。

    10.11Dockerfile の最小知識

    ここまでは他人が作った既製のイメージを使ってきた。自分でイメージを作るための設計図がDockerfileである。命令は多いが、最初に覚えるのは5つで足りる。

    命令意味例
    FROM土台にするイメージ。必ず1行目に書くFROM nginx:alpine
    RUNイメージを作るときに実行するコマンド（1行が1レイヤ）RUN apt-get update && apt-get install -y curl
    COPY手元のファイルをイメージの中へ入れるCOPY html/ /usr/share/nginx/html/
    CMDコンテナ起動時に動かす既定のコマンドCMD ["nginx", "-g", "daemon off;"]
    EXPOSEこのイメージが使うポートの申告（公開は -p で行う）EXPOSE 80
    ~/site/Dockerfile
    FROM nginx:alpine
COPY html/ /usr/share/nginx/html/
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
    イメージの構築と実行
    docker build -t mysite:1.0 . # . は Dockerfile のある場所
docker images mysite # 出来たイメージを確認
REPOSITORY   TAG   IMAGE ID       CREATED          SIZE
mysite       1.0   5b6c7d8e9f01   10 seconds ago   48.3MB
docker run -d --name mysite -p 8081:80 mysite:1.0

    -t 名前:タグ で名前を付ける。タグは省略すると latest になるが、1.0 のように自分でバージョンを振っておくと、更新して壊れたときに前の版へ戻せる（10.5節）。CMD に daemon off; を渡しているのは、nginxを背面に回さず前面で動かし続けるためである。コンテナは「最初のプロセスが終わったら終了する」ので、サービスを背面に回してしまうとコンテナが即座に終了する。これはコンテナ初学者がつまずく定番である。

    Note

    ※ ビルドしたイメージをそのままcomposeから使うこともできる。サービスの image: の代わりに build: . と書くと、docker compose up -d --build でビルドから起動までを一括で行える。第6回 6-1で自作イメージに挑戦する場合の入口である。

    Dockerfile
    イメージの作り方を1行ずつ書いた設計図。FROM で土台を選び、RUN や COPY で中身を積み、docker build -t 名前:タグ . でイメージにする。
    レジストリregistry / Docker Hub
    イメージを保管して配布する場所。nginx:alpine のようにレジストリ名を省くとDocker Hubが使われ、lscr.io/linuxserver/luanti は lscr.io というレジストリを明示した書き方である。

    10.12構成管理とクラウドの入口

    ここは実習の範囲を超えた一般的な基礎知識である。コマンドを打つ必要はないが、compose.yaml でつかんだ感覚がこの先どこへつながるのかを知っておくと、次に何を学ぶかを決めやすい。

    Infrastructure as Code と Ansible

    10.4節で述べたとおり、構成をコードとして書き、バージョン管理し、何度でも同じ環境を再現するのがInfrastructure as Code（IaC）である。compose.yaml が扱えるのはコンテナの構成だけだが、OSそのものの設定、すなわちユーザの作成、パッケージの導入、ufwのルール、ユニットファイルの配置まで含めてコードにしたい場面がある。そこで使われる代表的な道具がAnsibleである。

    Ansibleは、管理する側のマシンからSSHで相手のサーバに接続し、YAMLで書いた手順書（Playbook）のとおりの状態にする。相手側に専用のソフトを入れなくてよいのが特徴で、第3回 3-7で設定した公開鍵認証のSSHがそのまま通り道になる。重要な性質が冪等性で、「同じPlaybookを2回流しても、2回目は何も変更が起きない」ように書く。手順ではなく状態を書くという点は、composeと同じ発想である。

    AnsiblePlaybook / 冪等性
    SSH経由でサーバを「あるべき状態」にそろえる構成管理ツール。YAMLで書いた手順書をPlaybookと呼び、同じものを何度流しても結果が変わらないこと（冪等性）を目標に書く。
    実習ではここで使う

    ※ 最終課題のテーマ「構成管理・自動化」がこれにあたる。最小形と発展の例は付録A.5 構成管理・自動化にまとめてある。

    VPSやクラウドで同じことをするときの違い

    この実習で身に付けた手順は、レンタルサーバやクラウド（IaaS）上の仮想サーバでもほぼそのまま通用する。aptもsystemdもufwもDockerも同じである。違うのは、サーバが学内ネットワークの中ではなくインターネットに直接面している点と、使った分だけ課金される点である。

    観点実習のRaspberry PiVPS・クラウド
    アドレス学内LANのプライベートIP。外からは届かないグローバルIP。世界中から届く（不正アクセスも即座に来る）
    ファイアウォールサーバ内の ufw だけサーバ内の設定に加えて、事業者側のセキュリティグループでも絞る（二重）
    ログインパスワードでも実害が小さい公開鍵認証が事実上必須。パスワード認証は無効化する
    停止と復旧電源を入れ直せばよいコンソール機能から操作する。締め出されると復旧手段が限られる
    費用電気代のみ稼働時間、通信量、ディスク容量で課金。消し忘れが請求になる
    セキュリティグループsecurity group
    クラウド事業者が提供する、仮想サーバの手前に置かれるファイアウォール。サーバ内の ufw とは別物なので、両方で許可しないと通信は通らない。

    グローバルIPを持つサーバは、公開した直後からSSHへの不正ログイン試行を受ける。これは例外ではなく通常の状態であり、だからこそ公開鍵認証、更新の適用、fail2banといった対策が前提になる（第5章）。

    公開する前の安全確認リスト

    実習の範囲では学内ネットワークに閉じているが、将来どこかでサーバを外に出すときのために、確認すべき点を並べておく。どれも本実習で学んだ原則の再確認である。

    • 開いているポートを自分で説明できるか。sudo ss -tulnp と sudo ufw status numbered の結果を突き合わせ、理由を言えないポートは閉じる。
    • SSHはパスワード認証を無効にし、rootログインを禁止しているか（PermitRootLogin no）。設定を変える前に、締め出されたときの復旧手段を確認したか。
    • 初期パスワードや既定のアカウントが残っていないか。Luantiの管理者名（name）は自分で先に登録したか（第11章 11.4）。
    • 更新を当てる仕組みがあるか。ホストは apt upgrade、コンテナは docker compose pull と up -d が定期的に回っているか。
    • バックアップがあり、実際に復元して確かめたか（第4回 4-4）。
    • 公開ディレクトリに秘密情報を置いていないか。compose.yaml やスクリプトをGitに上げるとき、パスワードや鍵を含めていないか。
    • ログを見る習慣があるか。誰が入ってきているかを知らないサーバは、壊れていることに気付けない。
    注意

    ※ 本実習のサーバを学外に公開してはならない。ルータのポート開放やDDNSの利用は2.4 ネットワーク利用上の注意の規則に反する。上のリストは、卒業後や自宅の環境で自分の責任において公開するときのためのものである。
