    5-1マルチユーザシステム

    Linuxは誕生のときから、1台のコンピュータを複数の人間が同時に使うことを前提に設計されている。各ユーザには一意の番号（UID：User ID）が割り当てられ、ユーザは1つ以上のグループ（GID：Group ID）に所属する。ファイルの所有権もアクセス権もこのUID/GIDに基づいて管理される。実習でluantiユーザを作ってサービスを動かした（第3回 3-3）のは、このマルチユーザの仕組みを「権限の分離」に応用したものである。

    UID・GIDUser ID / Group ID
    ユーザとグループに割り当てられる一意の番号。Linuxが権限を判断するときに見ているのは、画面に表示される名前ではなくこの番号である。

    ユーザの情報は次のファイルに保存されている。これらは「設定はテキストファイルに保存される」というLinuxの原則の好例であり、catで中身を見ることができる。

    ファイル内容
    /etc/passwdユーザ名・UID・ホームディレクトリ・ログインシェルの一覧（名前に反しパスワードは入っていない）
    /etc/shadowパスワードのハッシュ値。rootのみ読める
    /etc/groupグループとその所属メンバーの一覧
    Note

    ※ パスワードは平文ではなく「ハッシュ値」で保存される。ハッシュは一方向の変換であり、元のパスワードには戻せない。ログイン時は入力をハッシュ化して保存値と比較する。パスワードを忘れたとき管理者でも「教える」ことができず「リセット」しかできないのはこのためである。

    5-2rootとsudo

    UID 0 のユーザをrootといい、すべての権限チェックを素通りできる特別な存在である。強力である反面、rm -rf の対象を打ち間違えるだけでシステムを破壊できる。そこで現代の運用では、rootで直接ログインする代わりに、一般ユーザとして作業し、必要なコマンドだけをsudoで実行する。

    rootUID 0
    すべての権限チェックを免除される管理者ユーザ。できないことがない代わりに、打ち間違い1つでシステムを壊せる。

    sudoには次の利点がある。

    1. root本人のパスワードを共有しなくてよい。
    2. 誰がいつ何を実行したかログに残る（journalctlで確認できる）。
    3. 操作のたびに「これは管理者権限が必要な操作だ」と意識する機会になる。

    sudoを使えるのはsudoグループ（ディストリビューションによってはwheelグループ）に所属するユーザだけであり、細かい許可設定は /etc/sudoers で管理される。

    sudosuperuser do
    1つのコマンドだけを管理者権限で実行するための道具。普段は一般ユーザのまま作業し、必要なときだけ権限を借りる、という運用を可能にする。

    この考え方を一般化したものが最小権限の原則である。「プログラムにもユーザにも、目的に必要な最小限の権限だけを与える」。実習でsudo権限を持たないluantiユーザを作ってサービスを動かしたのは、万一ゲームサーバが乗っ取られても、被害をそのユーザの権限の範囲に閉じ込めるためである。

    最小権限の原則least privilege
    目的に必要な最小限の権限だけを与えるという設計指針。サービス専用ユーザを作る、鍵ファイルを本人だけに読ませる、といった具体策はすべてこの原則の表れである。
    よくある誤解・トラブル sudo を付ければ何でも安全に実行できる

    sudo は「管理者として実行する」だけで、安全性は上がらない。むしろ普段なら失敗するはずの危険な操作が通ってしまう。sudo rm -rf を打つ前には、対象のパスを ls で一度確かめるとよい。

    Permission denied が出たら、とりあえず sudo を付ければよい

    Permission denied の原因は「所有者が違う」「ディレクトリにxが無くて入れない」など様々である。まず ls -l で所有者とパーミッションを見て、本来そのユーザが触るべきファイルなら chown で所有者を直すのが筋である。サービス用のファイルにsudoで書き込んでしまうと、以後そのサービスが自分のファイルを書けなくなることがある。

    5-3パーミッションの仕組み

    ファイルのアクセス権は、所有者・所有グループ・その他ユーザの3者それぞれに、r（読み取り）・w（書き込み）・x（実行）の3種類を設定する。ディレクトリの場合は意味が少し変わり、rは「中の一覧を見られる」、wは「中にファイルを作成・削除できる」、xは「中に入れる（cdできる）」である。

    数値表記はr=4、w=2、x=1の合計で表し、chmod 755 のように使う。よく使うパターンを覚えておくとよい。実際に chmod と chown を手で動かすのは第3回 3-1である。

    パーミッションpermission / rwx
    ファイルやディレクトリに設定されたアクセス権。所有者・所有グループ・その他の3者について、r（4）・w（2）・x（1）の組み合わせを3桁の数字で表す。
    数値記号典型的な用途
    755rwxr-xr-xプログラム・スクリプト、ディレクトリ
    644rw-r--r--一般的なファイル（他人は読めるが書けない）
    600rw-------秘密にしたいファイル（SSH秘密鍵、パスワードファイル等）
    700rwx------自分専用のディレクトリ

    なお、新規作成されるファイルのパーミッションの初期値はumaskという設定で決まる。また、/tmp のような共有ディレクトリには「作った本人しか消せない」ようにするスティッキービット（t）という特殊な権限が付いているなど、発展的な仕組みもある。ls -ld /tmp で確認してみてほしい。

    スティッキービットsticky bit / t
    /tmp のような誰でも書ける共有ディレクトリに付ける特殊な権限。全員がファイルを作れる一方、削除できるのは作った本人（と所有者・root）だけになる。
    よくある誤解・トラブル 権限エラーが出たら chmod 777 にすれば解決する

    777は「誰でも読み書き実行できる」という意味であり、問題を隠すだけで原因は直らない。必要なのはたいてい所有者の修正（chown）か、ディレクトリにxを付けることである。サーバ上で777を使う癖は、そのままセキュリティ事故につながる。

    SSHの秘密鍵を置いたのに公開鍵認証で接続できない

    秘密鍵のパーミッションが緩いと、SSHは安全でないとみなして鍵の使用を拒否する。秘密鍵は 600、~/.ssh ディレクトリは 700 が原則である（第3回 3-7）。

    5-4アカウントを操作するコマンド

    5-1節ではユーザとグループの仕組みを見た。ここでは、その仕組みを実際に動かすコマンドを整理する。サーバ管理者がユーザを触るのは、人を増やすときだけではない。第3回 3-3で作ったluantiユーザのように、サービスを動かすためだけの人間ではないユーザを作る場面のほうが、実務では多い。

    サービスアカウントservice account
    人間がログインするためではなく、特定のサービスを動かすために作るユーザ。実習のluantiユーザがこれにあたる。乗っ取られたときの被害をそのサービスの範囲に閉じ込めるために用意する。

    ユーザを作る・変える・消す

    Debian系のLinuxでは adduser と deluser を使う。これらは対話形式でホームディレクトリの作成まで面倒を見てくれる、初心者に優しいコマンドである。より低レベルの useradd / userdel もあるが、ホームディレクトリを自動では作らないなど挙動が異なるので、Raspberry Pi OSでは adduser を使えばよい。

    ユーザとグループの操作
    sudo adduser ユーザ名 # 基本形。パスワードなどを対話で聞かれる
sudo usermod -aG sudo ユーザ名 # sudoグループに追加する（-a を必ず付ける）
sudo passwd ユーザ名 # パスワードを再設定する
sudo adduser ユーザ名 グループ名 # 既存ユーザを既存グループに入れる書き方
sudo deluser --remove-home ユーザ名 # ユーザとホームディレクトリを削除する
    コマンドとオプション意味例
    adduser 名前ユーザを作り、ホームディレクトリと同名グループも作るsudo adduser luanti
    usermod -aG グループ 名前いま所属しているグループを保ったまま追加するsudo usermod -aG sudo taro
    usermod -s シェル 名前ログインシェルを変えるsudo usermod -s /usr/sbin/nologin luanti
    passwd自分のパスワードを変える（引数を付ければ他人の再設定、要sudo）passwd
    deluser 名前ユーザを削除する。--remove-home でホームも消すsudo deluser taro
    deluser 名前 グループグループから外す（ユーザは残る）sudo deluser taro sudo
    注意

    sudo deluser --remove-home ユーザ名 は、そのユーザのホームディレクトリを確認なしに丸ごと削除する。実習のluantiユーザに対してこれを実行すると、/home/luanti/server にあるワールドデータも一緒に消える。実習中にこのコマンドを使う場面は無い。どうしても必要なときは、先に ls -l /home/ユーザ名 で中身を確かめ、バックアップを取ってから実行すること。

    よくある誤解・トラブル sudo usermod -G sudo taro を実行したら、他のグループから外れてしまった

    -G は「所属グループをこの一覧に置き換える」という意味である。追加したいときは必ず -a（append）を付けて -aG とする。外れてしまった場合は sudo usermod -aG 元のグループ taro で戻せるが、sudoグループから自分が外れると復旧にモニタ接続が必要になるので特に注意する。

    グループに追加したのに、権限が増えていない

    グループの所属はログインしたときに読み込まれる。追加した本人は、いったんログアウトして入り直す（SSHなら接続し直す）まで反映されない。id で確認して古いままなら、まず接続し直すこと。

    いまの自分と相手を確かめる

    権限のトラブルは、たいてい「自分が思っているユーザと、実際に動いているユーザが違う」ことから起きる。作業の前後で確認する癖を付けたい。id と groups は一瞬で終わるので、su や sudo -i の直後には必ず打つとよい。

    ユーザ情報の確認
    whoami # 今のユーザ名だけ
id # UID・GID・所属グループをまとめて
id luanti # 他のユーザを調べる
groups # 所属グループ名の一覧
getent passwd luanti # /etc/passwd の該当行を引く

    出力の読み方：番号と名前の対応、そして所属グループの並びを見る。

    id と getent の出力例
    id
uid=1000(taro) gid=1000(taro) groups=1000(taro),4(adm),27(sudo),44(video),997(gpio)
id luanti
uid=1001(luanti) gid=1001(luanti) groups=1001(luanti)
getent passwd luanti
luanti:x:1001:1001:,,,:/home/luanti:/bin/bash

    1行目の groups= に 27(sudo) が含まれていれば、そのユーザはsudoを使える。2行目のluantiユーザには自分自身のグループしかない。これが「sudo権限を持たない専用ユーザ」であることの確認方法である（第3回 3-3）。getent passwd の出力は /etc/passwd の1行そのもので、コロンで区切られた7つの項目からなる。

    位置項目例の値意味
    1ユーザ名luantiログイン名
    2パスワード欄x実体は /etc/shadow にあるという印
    3UID1001一般ユーザは1000番台から
    4GID1001主グループの番号
    5コメント欄,,,氏名など。adduser で空欄にするとこうなる
    6ホームディレクトリ/home/luantiログイン時の初期位置
    7ログインシェル/bin/bash/usr/sbin/nologin ならログイン不可

    7番目の項目は覚えておく価値がある。Webサーバなどのサービス専用ユーザは、ログインシェルが /usr/sbin/nologin に設定されていることが多い。これは「このユーザではログインさせない」という設定で、乗っ取り対策の1つである。grep nologin /etc/passwd を実行すると、システムがどれだけ多くのサービス用ユーザを抱えているかが分かる。

    別のユーザとして実行する3つの方法

    実習では su - luanti を使ったが、似た目的のコマンドが他にもあり、混乱しやすい。違いは「相手のパスワードが要るか」「環境変数を引き継ぐか」「1コマンドだけか、入りっぱなしか」の3点である。

    書き方聞かれるパスワード環境使いどころ
    su - luantiluantiのパスワードluantiのものに入れ替わるluantiとして何度も作業する
    su luantiluantiのパスワード$HOMEなどが元のまま使わないほうがよい
    sudo -u luanti コマンド自分のパスワードおおむね元のまま1つのコマンドだけ試す
    sudo -i -u luanti自分のパスワードluantiとしてログインし直したのと同じパスワードを知らなくても入れる
    sudo -i自分のパスワードrootとしてログインし直したのと同じ管理作業を続けて行う
    別ユーザでの実行
    sudo -u luanti ls -l /home/luanti/server # luantiが本当に読めるかを試す
sudo -u luanti touch /home/luanti/server/test.txt # 書けるかを試す
sudo -u luanti rm /home/luanti/server/test.txt # 試した後片付け
su - luanti # luantiとして作業を続ける（パスワードが必要）
exit # 元のユーザに戻る

    sudo -u luanti は、サービスが起動に失敗したときの切り分けに非常に役立つ。「systemdが悪いのか、それとも権限が足りないのか」を切り分けるには、そのユーザになって同じ操作を手で試すのがいちばん速い。上の例で Permission denied が出れば、原因は chown のし忘れだと分かる。

    実習ではここで使う

    第3回 3-3 演習：サービスの非root化で adduser・chown -R・su - luanti を、第4回 4-2以降でluantiユーザとしてのバックアップ作業を行う。うまく動かないときは id と sudo -u luanti で切り分けるとよい。

    5-5sudoの設定を読む・書く

    5-2節で見たとおり、sudoが使えるかどうかはsudoグループへの所属で決まる。しかし実務では「特定のコマンドだけをパスワードなしで許す」といった細かい設定が必要になる。たとえば監視スクリプトからサービスを再起動させたいが、そのために管理者パスワードを自動化の仕組みに埋め込むのは避けたい、という場面である。その設定を行うのが /etc/sudoers と /etc/sudoers.d/ である。

    sudoers/etc/sudoers
    誰がどのコマンドをsudoで実行できるかを定めた設定ファイル。書式を誤るとsudoが一切使えなくなるため、必ず visudo 経由で編集する。
    注意

    /etc/sudoers を sudo vi で直接編集してはいけない。書式を1文字でも誤るとsudoがまったく使えなくなり、設定を直すためのsudoも使えないという状態に陥る。visudo は保存時に書式を検査し、誤りがあれば保存を拒んでやり直させてくれる。復旧にはモニタとキーボードを直接つないでrootで入る必要があるため、この一手間を省いてはならない。

    sudoの設定を安全に編集する
    sudo visudo # /etc/sudoers を検査付きで開く
sudo visudo -f /etc/sudoers.d/010-luanti # 追加設定を別ファイルとして作る（推奨）
sudo visudo -c # 現在の設定全体の書式を検査する
/etc/sudoers: parsed OK
/etc/sudoers.d/010-luanti: parsed OK
sudo -l # 自分に許されている操作の一覧を見る
    オプション意味例
    visudo検査付きで /etc/sudoers を編集するsudo visudo
    visudo -f ファイル指定したファイルを検査付きで編集するsudo visudo -f /etc/sudoers.d/010-luanti
    visudo -c編集せずに書式だけ検査するsudo visudo -c
    sudo -l自分に許可されているコマンドを一覧するsudo -l
    sudo -kパスワードを覚えている状態を破棄する席を離れる前に

    設定を追加するときは、/etc/sudoers 本体ではなく /etc/sudoers.d/ に新しいファイルを置くのが現代の作法である。本体を汚さないのでOSの更新時に衝突せず、不要になったらファイルごと消せばよい。ファイル名にドット（.）やチルダ（~）を含めると読み込まれないので、010-luanti のように英数字とハイフンだけで付ける。visudo -f で作れば、パーミッションも適切に設定される。

    /etc/sudoers.d/010-luanti（特定のコマンドだけ許可する例）
    # 監視スクリプトからLuantiサーバを再起動できるようにする
# 書式: ユーザ ホスト=(実行ユーザ) NOPASSWD: コマンドの絶対パス
taro ALL=(root) NOPASSWD: /usr/bin/systemctl restart luanti
taro ALL=(root) NOPASSWD: /usr/bin/systemctl status luanti

    1行の意味は「taroは、どのホストからでも、rootとして、パスワードなしで、この絶対パスのコマンドをこの引数で実行してよい」である。コマンドは必ず絶対パスで書く。which systemctl で確認できる。

    NOPASSWDは便利だが、安易に NOPASSWD: ALL と書くと、そのユーザはパスワードなしで何でもできるようになり、sudoを使う意味がほぼ失われる。NOPASSWDを許すのは、自動化のために必要な特定のコマンドだけにとどめるのが原則である。

    出力の読み方：誰が、いつ、どのコマンドをsudoで実行したかはすべてログに残る。

    sudoのログを読む
    journalctl _COMM=sudo -n 5 --no-pager
May 12 14:31:02 mc-24s1234 sudo[2411]:     taro : TTY=pts/0 ; PWD=/home/taro ; USER=root ; COMMAND=/usr/bin/systemctl restart luanti
May 12 14:35:40 mc-24s1234 sudo[2455]:     taro : TTY=pts/0 ; PWD=/home/taro ; USER=root ; COMMAND=/usr/bin/apt update
May 12 14:38:07 mc-24s1234 sudo[2478]: pam_unix(sudo:auth): authentication failure; logname=taro uid=1000 euid=0 tty=/dev/pts/0 ruser=taro rhost=  user=taro

    見るべきは、実行者（コロンの前の名前）、USER=（どのユーザとして実行したか）、COMMAND=（何を実行したか）の3つである。3行目の authentication failure はパスワードの入力ミスで、これが短時間に何度も並んでいれば、誰かが総当たりを試みている可能性を疑う。_COMM=sudo は「sudoというコマンドが出したログだけ」という絞り込みで、ログの読み方は第8章 8.1と第6章 6-7でさらに詳しく扱う。

    5-6パーミッション実用リファレンス

    5-3節で数値表記の読み方を学んだ。ここでは、実際にアクセス権を変えるコマンドと、初心者がはまりやすい落とし穴を扱う。chmod はパーミッション（何ができるか）を、chown は所有者（誰のものか）を変えるコマンドである。「権限が足りない」という症状に対して、どちらを直すべきかを見極めるのがこの節の目的である。

    chmod：数値と記号

    chmod には、755 のようにまとめて指定する数値表記と、u+x のように差分を指定する記号表記の2通りがある。「実行権だけ足したい」ような場面では、他の権限を壊さずに済む記号表記のほうが安全である。

    chmodの使い方
    chmod 600 ~/.ssh/id_ed25519 # 秘密鍵は本人だけが読み書きできる状態に
chmod 700 ~/.ssh # 鍵を置くディレクトリは本人専用に
chmod u+x ~/backup.sh # 所有者に実行権を足す（他はそのまま）
chmod go-w /home/luanti/server/luanti.conf # グループと他人から書き込み権を外す
ls -l ~/backup.sh # 結果を確かめる
-rwxr--r-- 1 taro taro 412 May 12 14:40 /home/taro/backup.sh
    書き方意味例
    数値3桁所有者・グループ・その他をまとめて指定するchmod 644 file
    u g o a対象（所有者・グループ・その他・全員）chmod a+r file
    + - =権限を足す・外す・そのとおりにするchmod u=rw file
    -Rディレクトリの中身にも再帰的に適用するchmod -R u+w dir
    --reference=ファイル別のファイルと同じ権限にそろえるchmod --reference=a.conf b.conf
    注意

    chmod -R 777 ディレクトリ は、その下のすべてのファイルを誰でも書き換え・実行できる状態にする。権限エラーはいったん消えるが、セキュリティ上の穴を開けただけで原因は何も直っていない。また chmod -R 755 のような指定も、本来実行する必要のないデータファイルにまで実行権を付けてしまう。ディレクトリとファイルで分けたいときは find ディレクトリ -type d -exec chmod 755 {} + と find ディレクトリ -type f -exec chmod 644 {} + のように find と組み合わせる。

    chown：所有者を直す

    「サービスがファイルを読めない」という症状の多くは、パーミッションではなく所有者の問題である。第3回 3-3でワールドデータをluantiユーザの持ち物にしたのは、まさにこの作業である。

    chownの使い方
    sudo chown luanti /home/luanti/server/luanti.conf # 所有者だけ変える
sudo chown luanti:luanti /home/luanti/server/luanti.conf # 所有者とグループを変える
sudo chown -R luanti:luanti /home/luanti/server # 中身もすべて変える
ls -ld /home/luanti/server # ディレクトリ自身の情報を見る
drwxr-xr-x 4 luanti luanti 4096 May 12 14:45 /home/luanti/server
stat -c '%a %U %G %n' /home/luanti/server # 数値表記と所有者だけを抜き出す
755 luanti luanti /home/luanti/server

    ls -l の代わりに stat -c '%a %U %G %n' を使うと、パーミッションを数値のまま確認できる。rwxr-xr-x と 755 を頭の中で変換する手間が省けるので、慣れないうちはこちらが読みやすい。ls -ld の -d は「ディレクトリの中身ではなくディレクトリ自身を見る」という意味である。

    よくある誤解・トラブル ファイルは644で誰でも読めるはずなのに、他のユーザが Permission denied になる

    ファイルにたどり着くまでのすべてのディレクトリにx（実行）権が必要である。ディレクトリのxは「中に入れる」という意味であり、これが無いと中のファイルの権限は見てもらえない。ls -ld /home/luanti /home/luanti/server のように上の階層から順に確かめるとよい。

    chmod -R でまとめて直したら、シェルスクリプトが動かなくなった

    再帰的な指定は、ディレクトリとファイルを区別しない。chmod -R 644 ならディレクトリからxが消えて中に入れなくなり、chmod -R 755 なら全ファイルが実行可能になる。上のfindと組み合わせる方法で直せる。

    umaskと、新しく作られるファイルの権限

    新しく作ったファイルが 644、ディレクトリが 755 になるのはなぜか。これはumaskという設定が「初期値から取り除く権限」を決めているためである。ファイルは 666、ディレクトリは 777 を出発点とし、そこからumaskの分を引いた値になる。

    umaskの確認
    umask # 現在の値（数値）
0022
umask -S # 記号で分かりやすく
u=rwx,g=rx,o=rx
touch /tmp/umask-test.txt
ls -l /tmp/umask-test.txt # 666 から 022 を引いて 644 になる
-rw-r--r-- 1 taro taro 0 May 12 14:50 /tmp/umask-test.txt
rm /tmp/umask-test.txt

    標準の 0022 は「グループと他人から書き込み権を取り除く」設定である。より厳しくしたい場合は umask 0077（自分以外は何もできない）を使う。~/.bashrc に書けばログインのたびに適用されるが、umaskは「これから作るファイル」にしか効かない点に注意する。既存のファイルは chmod で直す必要がある。

    umaskuser file creation mask
    これから作られるファイルやディレクトリから取り除く権限を決める設定。標準の 0022 では、ファイルは 644、ディレクトリは 755 で作られる。既存のファイルには影響しない。

    setuid：passwdコマンドが動く仕組み

    一般ユーザが passwd でパスワードを変えられるのは、よく考えると不思議である。パスワードの実体はrootしか読めない /etc/shadow にあるはずなのに、なぜ書き換えられるのか。答えがsetuidという特殊な権限である。

    setuidが付いたコマンドを見る
    ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 63960 Feb  7  2023 /usr/bin/passwd
ls -l /etc/shadow
-rw-r----- 1 root shadow 1042 May 12 09:12 /etc/shadow
find /usr/bin -perm -4000 -type f # setuidが付いたコマンドを探す
/usr/bin/passwd
/usr/bin/sudo
/usr/bin/su

    所有者の実行権の位置が x ではなく s になっているのがsetuidの印である。これは「このプログラムを実行している間だけ、実行者ではなくファイルの所有者（この場合root）の権限で動く」という意味である。だから passwd は一般ユーザが起動しても /etc/shadow を書き換えられる。sudo 自身がrootの権限を持てるのも、同じ仕組みによる。

    便利な反面、setuidの付いたプログラムに欠陥があれば、そこから誰でもroot権限を得られてしまう。自作のスクリプトにsetuidを付けるのは、原則として避けるべきである（そもそもLinuxのシェルスクリプトではsetuidは無視される）。必要な権限の委譲は、5-5節で見たsudoersで行うのが正しい方法である。

    setuidsetuid bit / rwsr-xr-x
    実行中だけファイルの所有者の権限で動くようにする特殊な権限。ls -l で s と表示される。passwd や sudo がこれにより動いている。

    5-7サーバセキュリティの基本原則

    権限の話は、そのままサーバのセキュリティの話につながる。この節は実習の範囲を越えた一般的な基礎であり、学内ネットワークの中だけで動く実習サーバには必要のない設定も含む。しかしいずれ自分のサーバをインターネットに公開するときには、ここに書いたことが最低限の出発点になる。考え方を先に知っておいてほしい。

    5つの原則

    1. 最小権限。ユーザにもプログラムにも、目的に必要な権限だけを与える。実習でluantiユーザを作ったのがこれにあたる。
    2. 攻撃面を小さくする。使わないソフトを入れない、使わないサービスを止める、開ける必要のないポートを開けない。攻撃者が触れる場所そのものを減らすのがいちばん確実である。
    3. 更新を当て続ける。侵入の多くは、既に修正が出ている欠陥を放置したサーバが狙われて起きる。
    4. 認証を強くする。推測できるパスワードを使わない。可能なら公開鍵認証に切り替え、パスワードログインを止める。
    5. 多層防御。1つの対策が破られても次で止まるように、独立した対策を重ねる。
    攻撃面attack surface
    外部から触れられる入口の総量。動いているサービス、開いているポート、インストールされたソフトの数だけ攻撃面は広がる。使わないものを減らすことが、そのまま防御になる。
    多層防御defense in depth
    性質の異なる対策を重ねて、1つ破られても被害が広がらないようにする考え方。ファイアウォール、公開鍵認証、専用ユーザ、fail2banはそれぞれ別の層にあたる。

    更新を当てる

    Debian系では、更新は apt で行う。apt update は「パッケージ一覧を最新にする」だけで、実際の更新は apt upgrade である点に注意したい（第1章）。

    更新の確認と適用
    sudo apt update # パッケージ一覧の更新
apt list --upgradable # 更新できるものを確認する
openssh-server/stable 1:9.2p1-2+deb12u3 arm64 [upgradable from: 1:9.2p1-2+deb12u2]
sudo apt upgrade # 実際に更新する
sudo apt autoremove # 不要になった依存パッケージを整理する

    更新の適用にはサービスの再起動が伴うことがあるため、学生や利用者がいる時間帯を避けるのが運用の常識である。自動で更新を当てる unattended-upgrades という仕組みもあり、個人のサーバでは有効にしておく価値がある。ただし自動更新は「気付かないうちにサービスが再起動される」ことを意味するので、何が自動で更新されるのかを理解したうえで使う。

    SSHを固める

    インターネットに公開したサーバのSSHポートには、数分と経たずに世界中から総当たりのログイン試行が来る。対策の基本は「パスワードで入れないようにする」ことである。第3回 3-7で公開鍵認証に切り替えたのは、その第一歩である。

    公開鍵認証public key authentication
    手元に秘密鍵、サーバに公開鍵を置き、パスワードを送らずに本人確認を行う方式。秘密鍵はパーミッション 600 で厳重に守り、絶対に他人に渡さない。
    /etc/ssh/sshd_config.d/10-hardening.conf（公開する場合の例）
    # rootで直接ログインさせない
PermitRootLogin no
# 公開鍵認証だけを許可し、パスワードログインを止める
PubkeyAuthentication yes
PasswordAuthentication no
# 認証に失敗し続ける接続を早めに切る
MaxAuthTries 3

    Debian 12 の /etc/ssh/sshd_config は先頭付近に Include /etc/ssh/sshd_config.d/*.conf という行を持つ。そのため、本体を書き換えるより、上のように /etc/ssh/sshd_config.d/ に設定ファイルを1つ置くほうが分かりやすく、元に戻すのもファイルを消すだけで済む。

    設定の検査と反映
    sudo sshd -t # 書式の検査（何も出なければ正常）
sudo systemctl restart ssh # 設定の反映
sudo systemctl status ssh # active (running) を確認
    注意

    PasswordAuthentication no を入れる前に、必ず公開鍵でログインできることを確かめること。鍵の設置に失敗したままこの設定を反映すると、誰もSSHで入れなくなる。手順は、（1）現在のSSH接続はつないだままにする、（2）別のターミナルから新しく接続して鍵で入れることを確かめる、（3）確認できてから元の接続を閉じる、である。締め出された場合の復旧手段は、Raspberry Pi にモニタとキーボードを直接つなぐことだけである。

    fail2banという層を足す

    公開鍵認証に切り替えても、ログイン試行そのものは来続ける。fail2banは、ログを監視して「短時間に何度も認証に失敗したIPアドレス」を一定時間ファイアウォールで遮断するソフトである。攻撃を根本から防ぐものではないが、ログの量を減らし、総当たりを現実的でなくする効果がある。多層防御の一層として広く使われている。

    fail2banの導入と確認
    sudo apt install -y fail2ban
sudo systemctl status fail2ban # active (running) を確認
sudo fail2ban-client status # 有効なjail（監視単位）の一覧
sudo fail2ban-client status sshd # SSHの監視状況

    出力の読み方：失敗の回数と、いま遮断しているIPアドレスの数を見る。

    fail2ban-client status sshd の出力例
    sudo fail2ban-client status sshd
Status for the jail: sshd
|- Filter
|  |- Currently failed: 1
|  |- Total failed:     37
|  `- Journal matches:  _SYSTEMD_UNIT=ssh.service + _COMM=sshd
`- Actions
   |- Currently banned: 2
   |- Total banned:     5
   `- Banned IP list:   203.0.113.45 198.51.100.7

    Currently banned がいま遮断中のIPアドレスの数、Total failed が起動以来の認証失敗の総数である。この数字が日々増え続けるのが、インターネットに公開されたサーバの日常であると知っておくとよい。Debian系では導入しただけでSSHの監視が有効になるが、環境によってはログの取得方法（backend）の設定が必要になることがあるので、fail2ban-client status にjailが表示されるかを必ず確かめる。

    fail2banfail2ban-client
    認証の失敗ログを監視し、短時間に失敗を繰り返すIPアドレスを一時的に遮断するソフト。総当たり攻撃を現実的でなくする、多層防御の一層である。

    公開してはいけないもの

    技術記事やリポジトリに作業の記録を載せるときは、次のものが混ざっていないかを必ず確かめる。第6回で記事を公開する前のチェックにも使ってほしい。

    • パスワード、APIキー、トークンの類（履歴 ~/.bash_history に残っていることもある）
    • SSHの秘密鍵（id_ed25519 など。公開鍵 .pub と取り違えないこと）
    • グローバルIPアドレス、学内ネットワークの構成、機器の設置場所が分かる写真
    • 学籍番号や氏名など、他人の個人情報
    • /etc/shadow や設定ファイルの中身をそのまま貼ったもの
    よくある誤解・トラブル 学内ネットワークの中だから、セキュリティは気にしなくてよい

    学内も多数の端末が繋がる立派なネットワークであり、感染した端末が内部から他を探すこともある。また、実習で身につけた手癖は、そのまま公開サーバでも出る。実習の環境こそ、正しい作法を練習する場であると考えたい。

    ファイアウォールを入れたから、もう安全である

    ファイアウォールは「開けたポートは通す」ものである。実習では22番（SSH）と30000番（Luanti）を開けており、その先で動くソフトに欠陥があれば通用しない。だから更新を当て、専用ユーザで動かし、認証を強くする層を重ねる（多層防御）。ファイアウォールの操作は第7章で扱う。

    ここまでの確認
    • id luanti の出力に sudo グループが含まれていないことを説明できる
    • sudo -u luanti コマンド で、そのユーザが読み書きできるかを試せる
    • /etc/sudoers は visudo 以外で編集してはいけない理由を言える
    • chmod -R 777 が解決策にならない理由を、自分の言葉で説明できる
